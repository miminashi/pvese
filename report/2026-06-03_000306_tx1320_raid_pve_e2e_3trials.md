セットアップ」が通しで動くこと**を確認する。

### 検証付き RAID Clear (ステップ1 詳細)

単一コマンドファイルの blind recipe (旧 r10hiicd 10/10) は高 latency 拠点で**先頭 `press ArrowRight`
(Main→Advanced タブ切替) がドロップ**して総崩れになる (**試行2 で実際に総崩れ**。試行1 は単一ファイル
で偶然成功。試行3 は最初から下記検証付き経路を使い、先頭 ArrowRight ドロップは再発したが `shot` 検証で
捕捉して retry した)。堅牢な手順:

1. `press ArrowRight` + `shot` → 画像で **Advanced タブ着地を確認** (Main のままなら ArrowRight 再送)
2. `navy 393 caret` → AVAGO MegaRAID 行へ **adaptive 着地** (ArrowDown drop 自己補正。
   隣接 LSI SW RAID 406 に overshoot しうるので指紋/行テキスト検証)
3. `Enter`×3 + `ArrowDown` → Clear Configuration 行 (右ヘルプ "Deletes all existing configurations" 確認)
4. modal commit を **1 ファイル**で投入 (`Enter`→`mouse 80 240`→`ArrowDown/Enter`×3 で No→Confirm→
   Enabled→Yes→commit→`Enter`→`Escape`→`ArrowDown`×2→`Enter`→`shot`)。vdm 指紋 **9758** = "no Virtual
   Drives currently available" = クリア成功。

## 試行で判明した知見と対応 (skill/doc/コード反映済み)

1. 🚨 **実 hostname = `tx1320`** (config は `training-tx1320`)。PVE は自 hostname を /etc/hosts で
   非ループバック IP に解決できないと **pve-cluster 不起動**。→ ラッパーが `ssh hostname` で **live
   hostname を採用** (試行1で発見、pve-cluster active を確認)。
2. 🚨 **eno2 DHCP リースは最終 PVE reboot で必ず変わる** (3試行とも .15/.17/.18 → **.16 に収束**)。
   → ラッパー `wait_ssh` が timeout 後に **/24 ping-sweep + MAC 再 discovery** で IP 差し替え。
   旧版 (`ip neigh | grep` のみ、ping-sweep なし) は neigh stale で発見できず試行1で verify を取り逃した
   (PVE 自体はインストール済みだった) → 修正後の試行2/3 は end-to-end 完走。
3. 🚨 **BIOS HII KVM Clear が唯一の脆弱リンク** (latency 36-340ms 依存)。単発キーのドロップ/誤登録
   (ArrowUp→ArrowRight でタブ移動) + stale frame が連鎖発生しうる → **recover (Manager.Reset) で
   KVM pipeline 健全化**が唯一確実な復旧。検証付き経路 + recover で 3/3 クリア成功。
4. deploy の DisconnectCD→HTTP400 / PowerOn "On"→ActionParameterValueNotInList は `|| true` ガード済み無害。
5. dark-net IP 使い回しで known_hosts に stale entry → `ssh-keygen -R` で掃除 (SSH 接続自体は可)。
6. `pve-setup-remote.sh` の z-fix-default-route フック (本拠点 GW ハードコード) は既に default route が
   ある限り発火せず無害。apt は eno1 (192.168.33.1) 経由で成功。

## 補足: 追加で判明した事実 (本文の主要知見以外)

- **A. RAID10 の検証根拠 (honesty)**: 各試行で `storcli /c0/vall show` を **インストール後の OS では
  実行していない** (storcli は OS に標準で入らない)。RAID10 判定は ① 単一ディスク `sda` が **1.6T**
  (4×900GB の RAID10 実効 = 1.6TB。RAID0 なら 3.3T / RAID5 なら 2.4T) + ② partman 成功 + OS boot +
  LVM (`tx1320-vg` root 1.6T + swap 23.9G) マウント成功 — から導いたもの。geometry 上 RAID10 で確実
  だが、コントローラの **"Optimal" ステータスを OS 上で直接読んではいない** (install 中の
  `/tmp/raid10-*.log` も未回収)。直読が必要なら OS 側に storcli64.bin を配置して確認する。
- **B. playground nginx access.log のクロックずれ**: タイムスタンプが実時間と整合せず (install の
  GET が数時間「過去」に見える) **リアルタイム相関に使えなかった**。完遂判定は **SOL モニタ
  (POWER_DOWN → PowerState Off) を正典**とした。nginx ログで進捗を追う際の注意点。
- **C. UEFI ブート順の挙動**: 最初の `boot-override Hdd` (Once) 消費後、**インストール済みディスクが
  既定ブートになる**ため、PVE セットアップの 2 回の reboot は boot-override を再設定せずにディスク
  起動した (= ラッパーが電源操作を持たなくてよい根拠)。
- **D. NIC MAC**: eno1 = `4C:52:62:14:A5:5C` / eno2 = `4C:52:62:14:DE:F0` (BIOS Advanced 画面で確認)。
  IP discovery に使うのは dark-net 側 eno2 (`…DE:F0`)。
- **E. ツール上の細かな観測 (本質でない)**: nginx 監視 Monitor (`tail -f | grep` over ssh) が install
  中イベントを emit せず (ssh/pipe バッファリング疑い) → SOL モニタに依存。`discover-ip.sh` の
  バックグラウンド出力がバッファされ `FOUND_SSH` 行が末尾に出ないことがある (再 discovery で確定)。
  `navy` は非収束時 (隣接 LSI 行 overshoot) に `presses=-1` を返す。
