## 前提・目的

### 背景

[2026-05-21_072829](2026-05-21_072829_tx1320_raid10_smb_n6_step2_irmc_dead_again.md) で iRMC SMB worker (FW 9.08F) が 5 経路すべて (`Manager.Reset` / `VirtualMediaServiceRestart` / `RemoteMountEnabled toggle` / OEM Action `ConnectCD` / 物理電源切離) で復活せず、 patched smbd の deploy 検証が無期限ブロックになっていた。

その際に副次的に「iRMC → 10.1.6.6 への TCP は 0 packet (proxy-ARP responder 未対応疑い)」と結論したが、 これは「SMB worker が死亡していたため socket すら open しなかった」が真因だった可能性が今回判明 (NFS では packet が flow したため)。

### 目的

SMB を諦め、 同じ OEM Virtual Media endpoint の **NFS モード** に切替えて attach 経路を確保することを実証する。

- 仮説: NFS worker と SMB worker は iRMC FW 内部で別 process である (通常の OS 実装パターン)。 → SMB worker 死亡から独立して NFS は生存しているはず
- 根拠: Fujitsu iRMCtools (公式) の `isomount` が `nfs://` URI 受理、 OpenStack Ironic `irmc-virtualmedia-deploy-driver` が `remote_image_share_type = NFS` を実装
- 不明: NFS が iRMC FW 9.08F の OEM PATCH endpoint で受理されるか、 ConnectCD action で attach 成立するか、 そもそも iRMC → 10.1.6.6 への NFS 経路が L2 到達可能か

### スコープ

**Phase 1 experiment のみ**: 10.1.6.6 に NFS server を立てて iRMC へ PATCH 試行 → tcpdump で TCP 到達確認 → ConnectCD で attach 成立確認 → SMB baseline へ rollback。 本格 deploy 統合 (`scripts/irmc-virtualmedia.sh` の NFS 対応拡張、 `config/training_tx1320.yml` の NFS keys 追加、 `scripts/tx1320-raid10-orchestrate.sh` Phase 5a 分岐) は次セッションへ。

## 結果サマリ (TL;DR)

🎉 **iRMC S4 FW 9.08F は OEM Virtual Media で NFS をサポートする (実機実証)**。

| 観測軸 | SMB (前ターンまで) | NFS (本ターン) |
|--------|-------------------|---------------|
| OEM PATCH `ShareType` 受理 | ✅ "SMB" のみ | ✅ **"NFS" 受理 + 永続化** |
| OEM Action ConnectCD POST | ✅ HTTP 204 だが silent no-op (5/20 以降) | ✅ **HTTP 204 + AllowableValues `["ConnectCD"]` → `["DisconnectCD"]` 遷移** |
| iRMC → 10.1.6.6 TCP packet | 0 packet (8 min 監視) | ✅ **146 packets (NFSv4 mount/getattr 連続)** |
| NFS/SMB server 側 log | 接続 0 件 | ✅ **NFS proc4 = 54 operations 処理** |
| iRMC OEM VM Members.count | 0 | 0 (host OFF 由来と推定、 12 min poll で変化なし) |

つまり SMB worker は死亡しているが、 **NFS worker は完全に生きていて、 iRMC は NFSv4 で `/var/samba/public` を mount + 内部 lookup まで完了している**。 host が OFF のため USB redirector の virtual media collection (`/redfish/v1/Managers/iRMC/VirtualMedia` Members) は populated されていないが、 これは host boot 時に解決すると推定 (本ターン未検証、 Phase 2 の領域)。

### 副次的な発見

1. **「iRMC → 10.1.6.6 は L2 不達」 の前ターン結論は誤り**: SMB worker が死亡していて socket が open されていなかったのが真因。 NFS では packet が大量に flow した (TCP 3-way handshake + NFSv4 ops 連続)。 deploy 先候補としても 10.1.6.6 は健在。
2. **NFS PATCH body は SMB と同じ schema (CDImage 配下)**、 `ShareType` を `"NFS"` に変えて `ShareName` を NFS export path (`/var/samba/public`) に書くだけ。 `UserName`/`Password` は空文字列でよい (iRMC が NFS では認証フィールドを ignore して null 化する挙動を確認)。
3. **iRMC は NFSv4 で client 接続している** (proc4 stat 54 ops、 v3 ではなく v4)。 plan で想定していた v3 強制は不要、 v4 で交渉成立。
4. **NFS は AutoAttach されない (RemoteMountEnabled=true でも)、 ConnectCD POST 明示が必要**。 SMB は (worker 死亡前は) AutoAttach で動いていたので、 NFS は手順が 1 step 増える (= PATCH → ConnectCD)。

### 経路 A: NFS PATCH (SMB と同じ endpoint、 ShareType="NFS" に書き換え)

```sh
ETAG=$(curl -sk --ciphers DEFAULT@SECLEVEL=0 --max-time 30 -u claude:Claude123 \
    -D - -o /dev/null \
    "https://10.254.254.9/redfish/v1/Systems/0/Oem/ts_fujitsu/VirtualMedia" \
    | sed -n 's/^[Ee][Tt][Aa][Gg]:[[:space:]]*\(.*\)\r\?$/\1/p' | head -1 | tr -d '\r"')

curl -sk --ciphers DEFAULT@SECLEVEL=0 --max-time 30 -u claude:Claude123 \
    -X PATCH "https://10.254.254.9/redfish/v1/Systems/0/Oem/ts_fujitsu/VirtualMedia" \
    -H 'Content-Type: application/json' \
    -H "If-Match: ${ETAG}" \
    -d '{"CDImage":{"Server":"10.1.6.6","UserName":"","Password":"","UserDomain":"","ShareType":"NFS","ShareName":"/var/samba/public","ImageName":"debian-preseed-tx1320.iso"},"RemoteMountEnabled":true}'
# → HTTP 200, レスポンス body の CDImage.ShareType="NFS" を確認
```

### 経路 C: ConnectCD POST (NFS は AutoAttach されないため明示必要)

```sh
curl -sk --ciphers DEFAULT@SECLEVEL=0 --max-time 30 -u claude:Claude123 \
    -X POST "https://10.254.254.9/redfish/v1/Systems/0/Actions/Oem/FTSComputerSystem.VirtualMedia" \
    -H 'Content-Type: application/json' \
    -d '{"VirtualMediaAction":"ConnectCD"}'
# → HTTP 204
# Action AllowableValues が ["ConnectCD"] → ["DisconnectCD"] に遷移すれば attach 成立
```

### D. NFS server proc 統計 (NFSv4 で 54 operations 処理)

```
proc4ops 76 0 0 0 6 1 0 0 0 0 40 9 0 0 0 0 7 0 0 1 0 1 0 44 0 1 1 0 0 0 0 5 0 0 3 0 ...
proc4    2  1  54
```

NFSv4 compound operations の内訳 (RFC 7530 op 番号):
- op 4 (ACCESS): 6
- op 10 (GETFH): 40
- op 11 (LINK): 9 — おそらく PUTFH カウンタとの集計か
- op 16 (OPEN_CONFIRM/PUTFH): 7
- op 23 (READDIR): 44
- op 31 (SETATTR): 5
- op 34 (SETCLIENTID 系): 3 等

= iRMC が NFSv4 で `/var/samba/public` の root を **mount + ディレクトリ列挙 + ファイル属性取得** を完了している。 これは「iRMC が NFS 経由で実際にメディア検査をした」決定的証拠。

### E. NFS server export 状態 (NFSv4 pseudo-root 自動 export)

```
/var/samba/public   10.0.0.0/8(ro,insecure,root_squash,all_squash,sync,wdelay,no_subtree_check,...,sec=1)
/                   10.0.0.0/8(ro,insecure,no_root_squash,sync,no_wdelay,no_subtree_check,v4root,...,sec=1)
/var/samba          10.0.0.0/8(ro,insecure,no_root_squash,sync,no_wdelay,no_subtree_check,v4root,...,sec=1)
/var                10.0.0.0/8(ro,insecure,no_root_squash,sync,no_wdelay,no_subtree_check,v4root,...,sec=1)
```

NFSv4 root pseudo-fs (`v4root`) が自動生成されており、 iRMC が NFSv4 で `/var/samba/public` 配下を navigate できる構成。

### F. Members.count はホスト OFF のため未反映 (12 min ポーリング)

`/redfish/v1/Managers/iRMC/VirtualMedia` の `Members@odata.count` は ConnectCD 後 12 分間 (24 iter × 5s + α) 0 のまま。

仮説: iRMC OEM 側は「attach 設定済」を AllowableValues=DisconnectCD で示しているが、 物理的に USB device を host に expose するためには host が ON である必要があり、 PowerState=Off の現状では DMTF VirtualMedia collection には反映されない。 host boot 時に解決すると推定。 (Phase 2 で実証)

### G. Rollback 結果 (SMB baseline へ正常復帰)

- DisconnectCD POST → HTTP 204 (NFS attach 解除)
- SMB PATCH (Server=10.1.6.1, ShareName=public, ImageName=debian-training-tx1320-raid10.iso, guest/guest) → HTTP 200
- 最終 `status` 出力: `CDImage.Server=10.1.6.1` / `ShareName=public` / `ImageName=debian-training-tx1320-raid10.iso` (前ターン baseline に完全復元)
- AllowableValues=`["ConnectCD"]` (SMB worker は死亡中のため、 attach は成立しない正常な baseline)

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🎯 iRMC S4 FW 9.08F は OEM Virtual Media で NFS をサポートする** (実機実証、 schema は SMB と同じ CDImage、 ShareType="NFS" + NFS export path + ImageName)。 SMB の代替経路として完全に利用可能
2. **🎯 NFS は AutoAttach されない**: SMB は RemoteMountEnabled=true + UsbAttachMode=AutoAttach で attach されていたが、 NFS は PATCH 受理だけでは attach せず ConnectCD POST 明示必須。 deploy スクリプトは PATCH → ConnectCD の 2 step
3. **🎯 「iRMC → 10.1.6.6 不達」 の前ターン結論は誤り**: 真因は SMB worker 死亡で socket open されていなかっただけ。 NFS では 7 秒で 146 packet flow、 deploy 先として 10.1.6.6 は健在 (proxy-ARP 経路は機能している)
4. **🎯 NFSv4 で交渉成立**: plan で想定した v3 強制は不要。 NFSv4 pseudo-root (`v4root` 自動 export) と組み合わせて iRMC は `/var/samba/public` を navigate
5. **`UserName`/`Password` は空文字列で OK** (NFS は IP based 認証)。 iRMC 側は null に正規化する
6. **NFS worker と SMB worker は iRMC FW 内で別 process**: SMB worker 死亡中でも NFS worker は完全に独立して active。 SMB 死亡時の bypass 経路として確立
7. **Members.count は host OFF で 0 のまま** (12 min poll、 ConnectCD 後も変化なし)。 USB redirector は host PowerState=On 時のみ DMTF VirtualMedia collection に出る可能性。 Phase 2 で host boot 経由で確認すること
8. **iRMC OEM PATCH の If-Match は quotes なし** (本ターン再確認、 既知 quirk)
9. **同期 tcpdump (foreground) は ssh & background で run_in_background 経由 launch すれば信頼できる**: ssh 接続が切れても server side で tcpdump が動き続けるが、 出力ファイル (pcap) の flush タイミングを timeout 終了で確実にするのが安全
