## 前提・目的

### 背景

Phase 3 (s-rustling-melody) で `quiet` 除去 + `earlyprintk` 追加でも SOL に kernel printk 0 行、 NFS pcap READ 0 packet、 KVM screenshot 全黒 (`tmp/fbd799f5/kvm-*.png` 3 ファイル全て **11857 byte 同一サイズ**) で 「kernel が startup できていない」 と結論された。

しかし以下 2 点が Phase 3 結論への重大な反証となった:

1. **ユーザ目視で「GRUB の後に Automated Install と表示されていた」** — Web UI 経由で実画面に GRUB メニュー表示が出ていた (= KVM 自体は alive)
2. **Phase 3 の KVM screenshot 3 ファイルが全部 11857 byte で完全一致** — これは `irmc-kvm-interact.py` の legacy `--capture-mode=canvas` で起きる WebGL `preserveDrawingBuffer:false` 由来の典型的な黒画 artifact (`scripts/irmc-kvm-interact.py:205-219` ドキュメンテーション参照)

過去レポート 2026-05-17_054151 で同スクリプトに `--capture-mode=locator` (default) が追加され、 `viewer_page.locator("canvas#kvm").screenshot()` を使えば composed frame を取得でき WebGL 黒問題を回避可能。

### 目的

Phase 4 として **iter3 = locator mode で KVM screenshot を時系列取得**し、 kernel が実際は boot しているのか (= Phase 3 結論の誤りで真因は console redirect 系) / 本当に死んでいるのか (Phase 3 結論補強) を切り分ける。

### BIOS 設定確認 (D-1 仮説の事前検証)

`scripts/irmc-bios.py backup + show` で 'redirect|console|serial|secure boot|boot mode' を grep:

```
SerialPort1                              | Serial Port                              | Enabled
SecureBoot                               | Secure Boot Control                      | Disabled
ChangeSettingsSerialPort                 | Change Settings                          | Auto
SecureBootMode                           | Secure Boot Mode                         | Custom
USBLegacySupport                         | Legacy USB Support                       | Enabled
Csm                                      | Launch CSM                               | Disabled
```

`Redirection After BIOS POST` / `Console Redirection` / `Terminal Type` 相当のエントリは BIOS XML に **存在せず**。 これは D3373 BIOS の仕様で、 iRMC SOL 経路は OEM Serial Multiplexer が COM2 → iRMC SOL を常時 proxy するため BIOS 側設定は不要 (UEFI Serial Console は EFI ConOut が自動)。

→ **D-1 (BIOS Console Redirection 切断) 仮説は弱まる**。 設定が無いものは切れない。 ただし、 UEFI ConOut の handoff そのものが kernel hang の原因である可能性は残る (kernel が UEFI Serial Console Protocol を引き継いだ直後に何かでつまずいて hang 〜 早期 panic)。

### regression diff (SMB session #6 5/18 との比較)

5/18 以降の commits:

```
f96d47b Add initrd preseed injection + cdrom-detect cmdline hints for TX1320
a87564c Fix generate-preseed.sh non-VLAN regression: x10dpu installer hang
```

`scripts/remaster-debian-iso.sh` の唯一の変更は f96d47b で、 内容は initrd preseed injection + `preseed/file=/preseed.cfg cdrom-detect/try-usb=true cdrom-detect/scan=true hw-detect/load_media=false` cmdline 追加 (`tmp/b0cc9d4d/remaster-diff-5-18.patch`)。 これらは **すべて preseed/cdrom-detect への入力**で、 kernel 早期 init には作用しない。 つまり SMB session #6 と Phase 4 の kernel 早期挙動に regression を生む直接因子は ISO build script レベルでは見当たらない。

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🎯🎯 KVM screenshot は必ず `--capture-mode=locator` を使う**: Phase 3 担当は legacy canvas mode (`canvas.toDataURL()`) を使い、 WebGL `preserveDrawingBuffer:false` の黒画 artifact (= 全 PNG が 11857 byte 完全一致) を「VGA 全黒」と誤判定した。 Phase 4 で同じ host を locator mode で撮ると BIOS POST 完全表示 + Booting Automated Install まで観測できた。 **`irmc-kvm-screenshot.py` (legacy) は今後使ってはいけない**。 必ず `irmc-kvm-interact.py screenshot --capture-mode=locator` (default mode) を使うこと。
2. **🎯 Phase 3 の本論 (kernel 早期 hang) は本セッションで補強された**: VGA に GRUB 最終出力 (Booting Automated Install + カーソル) が残ったまま kernel が画面更新を一切行わない = kernel が UEFI Boot Services を抜けた直後 / 早期 init で hang。 SOL printk も 0 のままで、 これは kernel が console を取得する地点まで到達していない強い証拠。
3. **🎯 BIOS XML に Console Redirection エントリが存在しない**: D3373 BIOS では UEFI Serial Console は EFI 標準 ConOut で自動化されており、 BIOS 側で切る/有効化する設定が無い。 D-1 (Console Redirection 切断) 仮説は本機では検証不可能で弱まる。
4. **🎯 `irmc-bios.py backup` の副作用**: backup は host を BIOS phase まで boot させるため、 `BootSourceOverrideTarget` を `None` にリセットする。 backup → boot-override 再設定 → Power On の順を守る必要あり。 orchestrate.sh への統合時に注意。
5. **🛑 SOL ring buffer リプレイは依然 false-positive 源**: Booting Automated Install が 48 回 SOL log に現れたが host は 1 回しか boot していない。 「複数回 boot 試行している」と誤読しないこと。
6. **📝 KVM locator screenshot の最適時系列**: t030/060/090/120 (~2 分は POST に費やされる) で BIOS POST 確認、 t180 で GRUB countdown 終了 + Booting Automated Install 出力、 t300 でその凍結を確認、 という timing が iRMC S4 FW 9.08F + D3373 BIOS で実証された。 Phase 5 以降でも同 timing を流用可能。
7. **🎯 真因候補は仮説 6/7/8/9/10 (kernel 早期 hang) のいずれか**: 次セッションは cmdline 細工 (`console=tty0` 除去 / `nousb` / `acpi=off` / `earlyprintk=efi,keep`) + GRUB image sanity + 別 boot media (HDImage) で切り分けを進める。 既知の難易度: 仮説 8 (iRMC NFS Virtual Media 固有) を確定するには SMB session #6 を再現する必要があり、 iRMC FW reflash がユーザ作業として必要になる可能性。
