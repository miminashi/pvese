### iter5 KVM 完全黒画 (2724 B × 5 同 sha256) の解釈

iter5 では BIOS POST も screenshot に映らず、 全 5 枚 (t030/060/120/180/300) が `64281268…` の同 sha256 で 2724 B (典型的な単色 PNG サイズ)。 これは:

1. **canvas mode artifact ではない** — script は `--capture-mode=locator` を明示指定
2. **タイミング差で BIOS POST 終了後を取った可能性** — ただし iter4 と power on 時刻差は 12 分 (cmdline 修正 + ISO build + scp + reload で経過)、 iter4 t030 (= power on +69s) で BIOS POST 映っていたので timing 差では説明しにくい
3. **`nousb` が iRMC Virtual VGA を間接的に切断した可能性** — iRMC の Virtual VGA は USB controller 経路で実装されている可能性があり、 GRUB が kernel cmdline `nousb` を見て USB 早期 disable → KVM viewer 経由の VGA 描画死亡 (kernel 起動失敗とは別現象)
4. **iRMC KVM session の偶発的失敗** — iter4 後の VM reload + connect-cd で何か iRMC 内部 state が変わった可能性

判定は (3) が最も有力だが、 確証は無い。 仮説 7 自体は kernel printk が出ないことから直接反証されており、 KVM 黒画は付随観測。

### GRUB image sanity 検証結果

| iter | local ISO sha256 | 10.1.6.6 remote ISO sha256 | 結果 |
|------|----------------|--------------------------|------|
| iter4 | `0a480c728d8d81fa2120d35702391ffc6032b382654a9fd5b1f36f077c467581` | (同) | ✅ 一致、 truncation なし |
| iter5 | `30a44ed071c09a1e6ef3df41cc858fef6710afba5ff46103f3c26ec091c0e005` | (同) | ✅ 一致、 truncation なし |

→ 仮説 10 のうち「scp 転送中 truncation」は確実に排除。 ただし「GRUB が iRMC USB CD-ROM emulation 経由で kernel image を不完全 read している」可能性は別途残る (GRUB shell `cat (cd0)/install.amd/vmlinuz | size` で次セッション検証要)。

## 未完了 / 次セッション課題 (Phase 6)

### 1. 🎯 最優先: 仮説 6/8/10 の切り分け

#### 1a. iRMC HDImage 経路 (仮説 8)

[[training_tx1320_hdimage_blocked]] memory では FDImage が `MaxDev=0` で blocked だが HDImage は未検証。 もし HDImage が attach できれば NFS Virtual Media 経路固有の問題 (仮説 8) かを直接判定できる。

#### 1b. GRUB shell で kernel image read 検証 (仮説 10)

Power on → GRUB countdown 中に `c` キーで command line に降り、 以下で kernel image の完全 read を確認:

```
grub> cat (cd0)/install.amd/vmlinuz | size
```

通常 `vmlinuz` size が判明している (build local で `xorriso -extract` で抽出して比較)。 USB CD-ROM emulation 経由で実際に read できる byte 数が ISO 内のサイズと一致しない場合、 仮説 10 (kernel image 不完全 load) が確定。

#### 1c. iter6-iter8 cmdline (仮説 7/9 反証後の補助)

| iter | 追加 cmdline | 目的 |
|---|---|---|
| iter6 | `acpi=off noapic` | D3373 ACPI quirk |
| iter7 | `pci=noacpi nolapic` | PCI/APIC 経路 |
| iter8 | `earlyprintk=efi,keep` | UEFI handoff 経路の printk 確保 |

優先度は仮説 6/8/10 切り分け後。

#### 1d. SMB session #6 再現 (NFS vs SMB の差分検証)

[[training_tx1320_smb_n6_step2]] で patched samba build 完了済だが iRMC FW 9.08F SMB worker 死亡で attach 不能。 FW reflash がユーザ作業として必要。

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🎯 仮説 7 / 9 はともに反証** — cmdline 細工 (`console=tty0` 除去 / `nousb`) では kernel printk 0 維持。 次は仮説 6/8/10 (iRMC NFS USB-CD timing / NFS Virtual Media 固有 / GRUB kernel image 不完全) に絞る。
2. **🎯 iter5 で KVM 完全黒画という新観測** — `nousb` cmdline が GRUB→kernel jump 前後で iRMC Virtual VGA に影響した可能性。 主因切り分けには影響しないが、 iRMC KVM の実装経路 (USB 関連?) を考える際のヒント。
3. **🎯 GRUB sanity (scp truncation 検証) は完全 clean** — local build と 10.1.6.6 NFS export の sha256 完全一致 (iter4/5 両方)。 仮説 10 のうち「scp truncation」は確実に排除、 残るは iRMC USB CD-ROM emulation 経由の read 量検証 (GRUB shell 経路)。
4. **🚨 cmdline 一時 patch を git checkout で revert する設計は危険** — session 開始時に `git status` で `M scripts/remaster-debian-iso.sh` がある場合、 `git diff` で patch 保存してから sed すること。 本セッションで Phase 3 修正 (uncommitted) を git checkout で破棄してしまった。
5. **📝 iRMC USB CD-ROM cache の reload は `disconnect-cd` → `connect-cd` で OK** — ImageName 維持で contents 差し替え時、 iRMC 側 cache を明示 reload。
6. **📝 KVM locator screenshot の sha256 一致は artifact ではない** — Phase 5 iter4 で t180/t300 の sha256 一致は「kernel hang で画面更新ゼロ」、 iter5 で全 5 枚一致は「VGA 描画停止」 (副次的)。 Phase 3 で「全 5 枚 11857 B 同一」 = canvas mode artifact の見極めポイントは **POST と hang で size が分かれるか否か** (artifact なら 1 種類のみ、 実 host hang なら 2 種類)。
7. **🎯 ISO build → scp → NFS publish → ConnectCD reload → boot の総時間は約 8 分** — orchestrate.sh build 約 3 分、 scp ~1 分、 disconnect/connect/mount ~1 分、 boot-override + Power On + KVM ~3 分。 cmdline 細工 iter の単位コスト目安。
