## 🎯 Phase 3a 重要新発見: WRITE SAME(16) は任意パターンを書ける

Phase 4c (前セッション) では「WRITE SAME(10) (0x41) は ASC=0x81 で reject」と確定していたが、**WRITE SAME(16) (0x93) は通る**ことが本セッションで判明:

| Opcode | コマンド | データ | 結果 |
|--------|---------|--------|------|
| 0x2a | WRITE(10) | zero/0xAA | ❌ ASC=0x81 |
| 0x8a | **WRITE(16)** (新試行) | zero | ❌ ASC=0x81 |
| 0x2e | **WRITE AND VERIFY(10)** (新試行) | zero | ✓ Good (実書込みなし、既存 zero と一致) |
| 0x2e | WRITE AND VERIFY(10) | 0xAA | ❌ ASC=0x81 ASCQ=0x01 (書込み発生で reject) |
| 0x8e | **WRITE AND VERIFY(16)** (新試行) | 0xAA | ❌ ASC=0x81 ASCQ=0x01 |
| **0x93** | **WRITE SAME(16)** (新試行) | **0x55 / 0xAA / DEADBEEF** | ✅ **Good、md5 一致確認、実書込み発生** |
| 0x89 | COMPARE AND WRITE | — | ❌ Illegal opcode (drive 非対応) |
| 0x8b | ORWRITE(16) | — | ❌ Illegal opcode |
| 0x9a | WRITE STREAM(16) | — | ❌ Illegal opcode |
| 0xa1 | ATA PASS-THROUGH | — | ❌ Illegal opcode (SAS のため当然) |

### WRITE SAME(16) の実証

`phase3a-wsame16.log` で以下を確認:
- W1: `0x55` パターンを LBA=4000 に 1 block 書込み → md5 一致
- W2: `DEADBEEF` パターンを LBA=5000 に 1 block 書込み → md5 一致
- W3: `0xAA` パターンを LBA=6000 から **8 blocks** 書込み → 全 8 blocks の md5 一致
- W4: `0x55` パターンを LBA=10000 から **1000 blocks** 書込み → 1 秒で完走、全 1000 blocks の md5 一致
- W5: `0xAA` パターンを LBA=20000 から **NUMBER_OF_LBAS=0 (= 残り全 LBA)** で発行 → DID_TIME_OUT (60 秒) 後も裏で実行継続、LBA=200000 / 2000000 の遠方 LBA まで `0xAA` で埋まったことを read-back で確認

### Linux ブロック層での実用性は限定的 (Phase 3b で確認)

WRITE SAME(16) は **同一パターンの繰り返し書込み** のみ可能で、任意データは不可。ZFS/ext4 等の通常 IO は WRITE(10/16) を発行するため救済できない。但し、以下は通る:

- `blkdiscard --zeroout -o <off> -l <len> /dev/sdb` (`write_zeroes_max_bytes=33550336` で WRITE SAME(16) 経由) → ✓
- `wipefs -af /dev/sdb` (zero 化のみ) → ✓
- `sgdisk -o /dev/sdb` (in-memory のみ。flush 時は WRITE(10) で ASC=0x81)
- **`mkfs.ext4 -F -E lazy_*=0 /dev/sdb`** → 大量の ASC=0x81 後 `Input/output error while writing out`、mount 失敗

### Phase 4c 結論の更新

前セッションのフィルタ表は次のように修正:

| 区分 | opcode | 通る/拒否 |
|------|--------|----------|
| ホスト OS の汎用 WRITE | 0x2a (WRITE 10), 0x8a (WRITE 16), 0x41 (WSAME 10), 0x8e (WAV 16 w/data), 0x2e (WAV 10 w/data) | ❌ ASC=0x81 |
| ディスク内部処理 | 0x04 (FORMAT), 0x07 (REASSIGN), 0x3f (WRITE LONG), 0x48 (SANITIZE), **0x93 (WRITE SAME 16)** | ✓ 通る |
| 実書込み無し | 0x2e (WAV 10 w/zero=既存と一致), 0x8e (WAV 16 同) | ✓ Good |

→ **Nutanix の opcode フィルタは「ホスト OS の汎用 WRITE 系のみ」を狙い撃ちしている**ことが、より精緻に確認された。WRITE SAME(16) が漏れている (= 仕様か穴かは不明) のは新事実。

### Phase 3c: Seagate firmware 入手 (失敗)

Playwright で次を網羅探索:

- openSeaChest GitHub releases → ユーティリティのみ、firmware なし
- GitHub code search (ST1200MM0088 / DKS5H) → ヒット 0
- Wayback Machine `seagate.com/files/.../EnterprisePerformance10K-v8/ST1200MM0088.LOD` → 404

**入手成功**: SeaChest Utilities 26.03.1 (`SeaChestUtilities.zip` 510 MB, login 不要)、SeaChest Lite (55 MB)。Linux x86_64 バイナリを Phase 3e で活用。

### Phase 3d: Microcode Download (LOD なしのためスキップ)

Phase 3c で .LOD 入手不可のため未実施。`SeaChest_Info` で `Firmware Download Support: Full, Segmented, Deferred` は確認済 (drive 側は受け入れ可だが、書き込む対象 firmware blob が無い)。

### Phase 3e: SCSI Mode Page Reset / vendor page (失敗)

`sdparm --all`, `sdparm --page=<hex>`, `SeaChest_Configure --showSCSIMP / --scsiMPReset` で網羅:

- 列挙された pages: 0x01 (RW Error Recovery), 0x02 (Disconnect-Reconnect), 0x03 (Format), 0x04 (Rigid Disk), 0x07 (Verify), 0x08 (Caching), 0x0a (Control), 0x19 (Protocol Specific), 0x1a (Power), 0x1c (IE)
- vendor specific page 0xF0-0xFF: **存在しない** (sdparm は abbreviation 不一致でエラー、SeaChest は invalid argument で reject)
- `scsiMPReset 3Fh-FFh / 0Ah-FFh / 18h-1Fh` → 全 "An Error occurred while trying reset" or "not supported"
- 各 reset 後の dd write 試行: 全 ASC=0x81 で失敗

→ Mode Page 経由のフィルタ無効化スイッチは **存在しない or アクセス不能**。

### Phase 3f: Broadcom sas3ircu (失敗)

GitHub mirror `CoolpeopleNetworks/SAS3IRCU_P16` から Linux x64 バイナリ取得:

- `sas3ircu list / 0 display`: ✓ 動作 (HBA = SAS3008, FW 16.00.10.00, BIOS 8.37.00.00、disk 認識正常)
- `sas3ircu 0 HWRESET noprompt`: **Invalid command** (P16 でサポート外)
- `sas3ircu 0 physpeed`: **Invalid command** (P16 サポート外)
- `sas3ircu 0 locate 1:0 ON/OFF`: ✓ 動作するが LED toggle のみ、write フィルタに影響なし
- `sas3ircu 0 BOOTIR`: "not supported by the firmware"
- `echo 1 > /sys/block/sdb/device/delete; echo "- - -" > /sys/class/scsi_host/host0/scan`: ✓ disk 復帰、write 試行は ASC=0x81 (Phase 2 と同じ結果)

→ HBA レベルの介入は drive firmware の opcode フィルタを解除しない (Phase 2 と整合)。

### Phase 3g: Nutanix AOS CE Live boot (実施不可)

Playwright で網羅探索:

- next.nutanix.com community-edition forum → 404 / 403 (要 login)

## 再現方法

### 1. pve10 を起動して再現環境準備

```sh
./oplog.sh ./pve-lock.sh run ./scripts/bmc-power.sh on 10.10.10.30 claude Claude123
./scripts/ssh-wait.sh 10.10.10.210 --timeout 300 --interval 10
ssh -F ssh/config root@10.10.10.210 "apt-get install -y sg3-utils sdparm blktrace"
```

### 2. WRITE(10) ASC=0x81 再現

```sh
ssh -F ssh/config root@10.10.10.210 "dd if=/dev/zero of=/dev/sdb bs=512 count=1 oflag=direct"
# → Remote I/O error
ssh -F ssh/config root@10.10.10.210 "dmesg -T --since '10 seconds ago' | grep ASC=0x81"
# → <<vendor>>ASC=0x81 ASCQ=0x0
```

### 3. WRITE SAME(16) で任意パターン書込み (新発見の再現)

```sh
ssh -F ssh/config root@10.10.10.210 sh -c "
  tr '\\0' '\\252' < /dev/zero | dd of=/tmp/aa bs=512 count=1
  sg_raw -s 512 -i /tmp/aa /dev/sdb 93 00 00 00 00 00 00 00 0f a0 00 00 00 01 00 00
  dd if=/dev/sdb bs=512 count=1 skip=4000 | md5sum
"
# → SCSI Status: Good
# → md5 一致 (33460dca3b35ad41df455259d2334079 = 0xAA pattern)
```

### 4. NUMBER_OF_LBAS=0 で disk 全体 fill

```sh
ssh -F ssh/config root@10.10.10.210 sh -c "
  timeout 60 sg_raw -s 512 -i /tmp/aa /dev/sdb 93 00 00 00 00 00 00 00 4e 20 00 00 00 00 00 00
  dd if=/dev/sdb bs=512 count=1 skip=2000000 | md5sum
"
# → DID_TIME_OUT (OS 側) 後も裏で実行継続、遠方 LBA も 0xAA で埋まる
```

### 5. Linux ブロック層での実用化試行 (失敗)

```sh
ssh -F ssh/config root@10.10.10.210 mkfs.ext4 -F -E lazy_journal_init=0,lazy_itable_init=0,nodiscard /dev/sdb
ssh -F ssh/config root@10.10.10.210 mount /dev/sdb /mnt/test
# → 大量の ASC=0x81 後、最終的に "Input/output error while writing out and closing file system"、mount 失敗
```

## 次回セッションへの引き継ぎ事項

### 確定した制約 (claude リモート不可)

1. **Nutanix Portal アクセス**: ISO/firmware 入手は claude 自動化不可 (account 登録 + reCAPTCHA + 認証メール)
2. **物理ジャンパ確認**: 現地作業 (リモート不可)
3. **HBA / Drive ハードウェア交換**: 物理作業

### 残された可能性 (claude 実施可能だが期待値極めて低)

- **AOS CE ISO 取得を人手で行い SMB share に配置**: ユーザが手動で ISO を `\\public\` 等に置けば、claude 側で `bmc-virtualmedia.sh` 経由で mount し、Live boot + `genesis stop` / `disk_release` 試行可能。ただし Nutanix が opcode フィルタを drive firmware に焼いた時点で、ホスト OS の側 (AOS 含む) からは解除できない可能性が高い。
- **DKS5H-J1R2SS の Seagate generic firmware (.LOD)**: 別経路 (Seagate 公式 portal account) でユーザが取得すれば claude 側で `sg_write_buffer --mode=7` で書き換え試行可能。brick リスク受容済。

### 実用上の判断

**10-13号機の Seagate DKS5x データ HDD は read-only として扱う**ことが Phase 2 で確定済。本セッションは:

- 否定的結論を強化: Mode Page / HBA reset / vendor opcode 全網羅で **解除手段なし** を確定
- 肯定的副産物: **WRITE SAME(16) で任意パターン埋込み可能** (実用は限定的だが理論研究上重要)
- 下流タスク: 10-13号機をストレージ用途から外し、別 HW (4-9号機) で LINSTOR/ZFS 運用継続

### Issue #61 の更新方針

完全ギブアップで blocked 継続。新しい blocked 理由 (Phase 2 を更新):

> Phase 1-3 全て効果なし。Nutanix firmware Rev 7FA9 の opcode フィルタは **WRITE(10/16)/WSAME(10)/WAV(10/16) を vendor reject** し、**FORMAT/SANITIZE/WRITE_LONG/REASSIGN/WSAME(16)** は通す精緻な選別を実装。Phase 3 で SeaChest 26.03.1, sas3ircu P16, Mode Page Reset 全 vendor page を試行するも解除不能。Nutanix AOS CE は portal login wall で claude 自動取得不可。Seagate generic firmware も入手不可。本ハードウェアでの LINSTOR/ZFS 運用は事実上不可能で確定。**WRITE SAME(16) のみ任意パターン書込み可能** (新発見、ファイルシステム化には不十分)。
