## 実施内容と結果

### Phase α: BIOS Setup 再進入 (部分達成)

`setup-raid10 --continue-from=S1 --stop-at=S5 --session=run-a` で実行。 結果:

- S1 Manager.Reset GracefulRestart: HTTP 204 受理
- S1 BMC up 検出: 4 秒で 200 → **誤検出** (curl が Reset 開始前に応答)
- S2-S5: 直後の KVM 接続が `ERR_CONNECTION_REFUSED` で全て失敗 (BMC は実際にはまだ reset 進行中)
- 約 130 秒後に BMC 復帰、 ホストは前セッションの最終状態 (BIOS Setup Advanced タブ、 cursor on AVAGO) を保持していた

**新発見 (バグ)**:

1. **S1 BMC 復帰待ちの race condition**: `Manager.Reset` POST 後に BMC が即座に reset するわけではなく、 数秒 〜 数十秒のラグがある。 dispatcher の S1 は `sleep 3` 後に最初のポーリングを行うため、 reset 開始前の HTTP 200 を「復帰完了」と誤検出する。 → **修正済み**: `sleep 30` の事前待機を入れ、 ポーリング間隔も 3s → 5s に変更
2. **S2 `bmc-power.sh off` は存在しないサブコマンド**: `forceoff` が正しい (`bmc-power.sh` の `case` 文に `off` が無い)。 結果として S2 の forceoff が無効化されており、 これがたまたま「ホストが前回 BIOS Setup 状態のまま」だった理由 → **修正済み**

### Phase β: AVAGO HII 進入 → キーシーケンス探索 (部分達成 + 中断)

ホストが BIOS Setup Advanced で AVAGO 行ハイライト状態であることを OEM Screenshot で確認後、 Enter キーを 1 回送信 → **AVAGO MegaRAID Configuration Utility Main 画面に進入成功** (Drives=4, VDs=0)。

ここから先の M2 (Main Menu submenu) で KVM キーボードが完全に反応しなくなった。

### 重要な新発見

#### (A) BMC OEM Screenshot pipeline は **連続 Make POST で 200s+ 完全停止する**

連続して `FTSScreenshotType: Make` POST を投げると、 `AllowableValues` に `Preview` が永続的に現れなくなる。 前セッションでは「60-90s で自動回復」と書かれていたが、 本セッションでは **5+ 分待機しても回復せず** (KVM 経由のキー操作中も継続)。

**回復手順** (実証):
- `POST /redfish/v1/Managers/iRMC/Actions/Manager.Reset {"ResetType":"GracefulRestart"}` で BMC リブート (HTTP 204)
- ~170s 待機後、 BMC 復帰直後の最初の OEM Screenshot は **必ず成功**する (attempt 1)
- ただし続く数回の Make POST で再度 pipeline が詰まる

**コスト**: Manager.Reset 1 回あたり 200s + その後の screenshot 数回までで pipeline 再詰まり。 1 milestone あたり最悪 250s+ の所要時間。

**新スクリプト修正**: `scripts/irmc-oem-screenshot.sh` の curl `--max-time` を **4s → 15s に増加**。 BMC が高負荷時に `Systems/0` GET に 7-8s 要するケースがあり、 4s では永久に Preview を取得できなかった。

#### (B) **Playwright 経由のキー送信 + canvas screenshot が共に失敗** (本セッション中断原因)

**2026-05-17 追加検証 (ユーザ手動)**: 本セッション後にユーザが手動 Web UI から HTML5 KVM を開いたところ、 **BIOS 画面のキー操作は問題なく可能、 ブラウザ開発者ツールから `#kvm` ノードのスクリーンショットも正常に取得できる** ことが確認された。 つまり BMC 側 (USB HID emulation、 frame buffer 配信) は健常で、 **問題は本セッションが使った Playwright 自動化スクリプト (`scripts/irmc-kvm-interact.py`) 側にある**。

##### B-1. canvas screenshot が全て真っ黒 (`11857 bytes` 固定) の原因 — **WebGL `preserveDrawingBuffer: false` パターンと推定**

`irmc-kvm-interact.py` の `capture()` は:
```js
document.getElementById('kvm').toDataURL('image/png')
```
を `page.evaluate()` 経由で実行する。 これが常に画素 sum = 0 の真っ黒 PNG を返す一方で、 DevTools の「ノードのスクリーンショット」は実画面を取得できる。 典型的な症状: **`#kvm` が WebGL canvas (`getContext('webgl')` か `webgl2`) で、 viewer.min.js が `preserveDrawingBuffer: false` (default) で作っている**。 default 設定だと frame 合成後にバックバッファがクリアされ、 `toDataURL()` / `getImageData()` は黒を返す。 DevTools は OS ディスプレイ側の合成済みフレームを別経路でキャプチャするので影響を受けない。

##### B-2. キー送信が host に届かない原因 — **focus / 信頼イベント / target 要素の問題と推定**

`focus_kvm()` は `processing_maindiv` overlay を hide → `canvas#kvm.focus()` → `viewer_page.click('canvas#kvm', force=True)` の順で focus 確立を試みる (`scripts/irmc-kvm-interact.py:110-133`)。 ただし viewer.min.js のキーイベント listener が `document` レベルで貼られている場合 (一般的)、 canvas クリックで activeElement が canvas になるだけでは listener に届かないケースがある。 また headless Chromium の click は `force=True` で hit-test を bypass するため、 viewer.min.js の内部状態 (KVM session が active か否か) が想定外になることがある。

候補となる回避手段 (次セッションで検証要):

1. **Playwright の要素単位 screenshot**: `viewer_page.locator('canvas#kvm').screenshot(path=...)` または `viewer_page.screenshot(clip={x,y,width,height})` でディスプレイ側の合成済みフレームを取得 (WebGL preserveDrawingBuffer に左右されない)
2. **canvas screenshot を頭から放棄して `locator.screenshot()` 一本化** にスクリプト改修
3. **キー送信は `page.keyboard.press` の前に `viewer_page.locator('canvas#kvm').click()` で実 hit-test 経由のクリック** を実施 (force=True を外して overlay 隠しの完全性を担保)
4. **`document.dispatchEvent(new KeyboardEvent('keydown', {key: 'Enter', code: 'Enter', bubbles: true}))`** を `page.evaluate()` 経由で送る (viewer.min.js の listener が document 上にあるなら届く可能性)
5. **Playwright を non-headless で起動して目視確認**: `--no-headless` で X11 forward (本ローカルマシンに DISPLAY あり? 要確認)、 もしくは Playwright trace + video 録画で正確な失敗位置を切り出す
6. **canvas に直接 keyboard.down/up を発行**: `viewer_page.locator('canvas#kvm').dispatch_event('keydown', {key: 'Enter'})` で要素単位の合成イベント

優先順位は 1 + 3 が最も確度高い (canvas screenshot 修正 + 正しい focus → keyboard.press)。 2 は 1 が成功した場合の整理用。 4 はバックアップ。 5/6 は他が全滅した場合の保険。

#### (C) AVAGO HII への進入は **Enter 1 回で成功** (確定)

前セッションで cursor が AVAGO 行に居る状態から `sendkeys:Enter` 1 回で AVAGO MegaRAID Configuration Utility Main 画面 (Properties セクション + Status [Optimal] + Drives 4 / Drive Groups 0 / Virtual Drives 0 / Configure 等の表示) に進入することを実機確認 (`avago_main.jpg` 添付参照)。

これは前セッションでは未確認 (BMC overload で screenshot が取れなかった) の事実。

#### (D) AVAGO HII Main 画面のレイアウト (確定)

cursor 起動位置は **`Main Menu`** 行 (▶ 印付き)。 右ペインの説明は "Shows menu options such as Configuration Management, Controller Management, Virtual Drive Management, Drive Management and Hardware Components."

画面構成 (上から下):

### 1. **`irmc-kvm-interact.py` のリファクタ — Playwright 自動化を実働化** (2026-05-17 追記)

ユーザ手動検証で **BMC 側は健全** と確定したため、 次セッションの最優先タスクは Playwright スクリプトの修正:

#### (A) canvas screenshot 取得経路の置き換え

現状 `capture()` は `canvas.toDataURL()` を使っているが、 viewer.min.js が WebGL `preserveDrawingBuffer: false` で canvas を作っていると思われる (推定)。 改修:

```python
# 現状 (動かない、 全て黒)
def capture(viewer_page, output):
    data_url = viewer_page.evaluate("""() => {
        const c = document.getElementById('kvm');
        return c ? c.toDataURL('image/png') : null;
    }""")
    png = base64.b64decode(data_url.split(",", 1)[1])
    open(output, "wb").write(png)

# 改修案 1: locator.screenshot() で要素単位合成済みフレームを取得
def capture(viewer_page, output):
    viewer_page.locator("canvas#kvm").screenshot(path=output)

# 改修案 2: page.screenshot(clip=...) で領域指定
def capture(viewer_page, output):
    box = viewer_page.locator("canvas#kvm").bounding_box()
    viewer_page.screenshot(path=output, clip=box)
```

改修後、 「`force-refresh` step (Control x3 + canvas resize event)」「`capture_with_retry` の黒判定リトライ」は不要になるはず (DevTools で正常取得できる経路を採るため)。

#### (B) キー送信前の focus 確立を実 hit-test 経由に

```python
def focus_kvm(viewer_page):
    # overlay 隠し (現状維持)
    viewer_page.evaluate("""() => {
        const overlay = document.getElementById('processing_maindiv');
        if (overlay) overlay.style.display = 'none';
        document.querySelectorAll('.processing_bg, .processing_bg_inner')
            .forEach(el => el.style.display = 'none');
    }""")
    # 改修: force=True を外して実 hit-test 経由のクリック
    # overlay が完全に隠れていない場合はここで Playwright が警告する
    viewer_page.locator("canvas#kvm").click(timeout=5000)
    # 念のため focus も
    viewer_page.evaluate("document.getElementById('kvm').focus()")
    time.sleep(0.3)
```

加えて `force=True` をやめると viewer.min.js の native event listener が「ユーザ操作起点」として扱える可能性。

