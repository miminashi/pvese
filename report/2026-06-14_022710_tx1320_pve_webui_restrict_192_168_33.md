# tx1320 PVE Web UI + API アクセスを 192.168.33.0/24 に制限

- **実施日時**: 2026年6月14日 02:27 (JST)

## 添付ファイル

- [実装プラン](attachment/2026-06-14_022710_tx1320_pve_webui_restrict_192_168_33/plan.md)

## 前提・目的

セットアップ済みの training-tx1320 (Fujitsu PRIMERGY TX1320 M3) の Proxmox VE で、
PVE 管理画面 (Web UI) および REST API へのアクセスを **192.168.33.0/24 ネットワークからのみ** 許可し、
それ以外のネットワーク (特に claude が運用に使っている 10.254.254.0/24 dark-net) からは遮断する。

- 背景: Web 管理画面・API を特定ネットワークからのみ利用可能にしてアクセス面を絞りたい
- 目的: pveproxy (8006) を 192.168.33.0/24 + loopback に限定し、SSH (22) は維持する
- ユーザ確定事項:
  - 対象 = Web UI + API (= pveproxy 8006)、SSH は開けたまま
  - 適用範囲 = **現ホストのみ** (リポジトリのセットアップスクリプトには組み込まない)
  - 許可元 = 127.0.0.1 (loopback) + 192.168.33.0/24、それ以外は全拒否

### 重要な前提

- PVE の **Web UI と REST API は同一の `pveproxy` (TCP 8006)** で提供される。8006 を絞れば両方が同時に制限される。
- SSH (22) は pveproxy と別系統のため、pveproxy のアクセス制限の影響を受けない (= 管理・復旧経路として残る)。
- PVE firewall / iptables ではなく `/etc/default/pveproxy` の `ALLOW_FROM` を採用 (pveproxy にのみ作用する最小影響・低リスクな公式機構)。

## 環境情報

- ホスト: training-tx1320 / Fujitsu PRIMERGY TX1320 M3 / config: `config/training_tx1320.yml`
- PVE: pve-manager (Debian 13 ベース、HW RAID10 / LVM)
- NIC 構成:
  - **eno1 = 192.168.33.11/24** (サイト LAN、OpenWrt NAT 背後。claude からは到達不可)。**DHCP 動的リース** (`dynamic`、valid_lft 約9時間)、MAC `4c:52:62:14:a5:5c` (altname `enp3s0` / `enx4c526214a55c`)。host IP は /24 内で変動し得るが、制限は /24 サブネット単位なので影響しない
  - **eno2 = 10.254.254.16** (dark-net DHCP、MAC `4c:52:62:14:de:f0`。claude が SSH/Web で到達している経路)
- pveproxy: 適用前はアクセス制限なし。listen socket を直接確認 → `*:8006` で **dual-stack listen** (IPv4 + IPv6 両方で接続を受ける)
- `/etc/default/pveproxy`: 適用前は **未存在** (デフォルト動作。新規作成した)

## 実施内容

`/etc/default/pveproxy` を新規作成し、以下を設定した:

```
ALLOW_FROM="127.0.0.1,192.168.33.0/24"
DENY_FROM="all"
POLICY="allow"
```

`POLICY="allow"` 下では `DENY_FROM="all"` で全拒否しつつ `ALLOW_FROM` 一致を許可 (ALLOW が DENY に優先)。
結果として 127.0.0.1 と 192.168.33.0/24 のみ許可され、それ以外は接続段階で拒否される。
適用後 `systemctl restart pveproxy` を実行。

## 検証結果

| テスト | 送信元 | 適用前 | 適用後 | 判定 |
|--------|--------|--------|--------|------|
| Web UI (`https://:8006/`) | claude (10.254.254.16) | 200 | 接続不可 (000) | ✅ 遮断 |
| API (`/api2/json/version`) | claude (10.254.254.16) | 401 (認証要求 = 到達) | 接続不可 (000) | ✅ 遮断 |
| Web UI | loopback (127.0.0.1、ホスト上) | — | 200 | ✅ 許可 |
| Web UI | eno1 (192.168.33.11、ホスト上) | — | 200 | ✅ 許可 |
| Web UI | dark-net 自己接続 (10.254.254.16、ホスト上) | — | 接続不可 (000) | ✅ 遮断 |
| SSH (22) | claude → 10.254.254.16 | OK | OK | ✅ 維持 |
| pveproxy サービス | — | active | active | ✅ 稼働 |

- pveproxy は不許可 IP を **TLS 接続確立前に切断** する挙動 (curl exit 35 / http_code 000)。403 を返すより手前で弾くため、より強い遮断となっている。
- API の適用前 401 は「認証トークン未指定だが pveproxy には到達している」状態。適用後は送信元 IP に基づき TLS 層で切断 (000) されるため、Web UI と同様に遮断成立を確認。

## 再現方法

1. tx1320 の現 IP を eno2 MAC で特定 (DHCP で変動するため):
   ```sh
   # 10.254.254.0/24 を ping-sweep 後
   ip neigh | grep -i 4c:52:62:14:de:f0
   # → 10.254.254.16 (例)
   ```

2. `/etc/default/pveproxy` に以下を設定 (既存の同名キーは除去してから追記、冪等):
   ```
   ALLOW_FROM="127.0.0.1,192.168.33.0/24"
   DENY_FROM="all"
   POLICY="allow"
   ```

3. pveproxy 再起動:
   ```sh
   systemctl restart pveproxy
   systemctl is-active pveproxy
   ```

4. 検証:
   ```sh
   # claude 側 (10.254.254.x) → 接続不可 (000) になること
   curl -sk -o /dev/null -w '%{http_code}\n' https://10.254.254.16:8006/
   # ホスト上 loopback / eno1 → 200 になること
   curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8006/
   curl -sk -o /dev/null -w '%{http_code}\n' https://192.168.33.11:8006/
   ```

## 復旧手順

`/etc/default/pveproxy` は今回新規作成したため、制限を完全に解除するには同ファイルを削除し
`systemctl restart pveproxy` を実行すればよい (デフォルトの全許可動作に戻る)。
SSH は遮断していないため、いつでも復旧操作が可能。

## 補足・発見事項

- ユーザ指定により **リポジトリのスクリプト/設定は変更していない** (現ホストのみ適用)。
  tx1320 を再インストールするとこの設定はリセットされる。
- PVE 公式のアクセス制限機構 (`/etc/default/pveproxy` の `ALLOW_FROM` 等) はこのリポジトリでの初使用。
- **IPv6 の扱い (注意点)**: pveproxy は `*:8006` で dual-stack listen しており IPv6 でも接続を受けるが、
  `ALLOW_FROM` は IPv4 (`127.0.0.1` / `192.168.33.0/24`) のみを列挙している。
  このため **IPv6 loopback `::1` を含む全ての IPv6 送信元は拒否される** (実機で `https://[::1]:8006/` → curl exit 35 / 000 を確認)。
  通常 PVE のホストローカル通信は 127.0.0.1 / pvedaemon ソケット経由なので実害は低いが、
  `::1` で 8006 を叩くツールがある場合は `ALLOW_FROM` に `::1` 追加が必要。
- **遮断の挙動 (補足)**: 不許可 IP に対し pveproxy は TCP は accept するが TLS handshake を完了させずに切断する
  (curl exit 35 = "SSL connect error"、connection refused = exit 7 ではない)。IPv4・IPv6 とも同じ挙動。
