## 前提・目的

前セッション (s-twinkly-boole) で **N6 仮説 = iRMC が qfsinfo level=513 (0x201) を全 retry cycle で要求するが Samba 4.19.5-Ubuntu は NT_STATUS_INVALID_LEVEL を返す** ことが Samba debug log (`samba-empty-n2.log` 4017 行) で確定した。 真因候補が「smb_posix_open より前 (qfsinfo phase)」にあると判明したのは前進だが、 仕様上 0x201 の正規意味は推察止まりだった。

本セッションは N6 検証 step 1 として、 **(a) Samba 4.19.5 ソースで level=513 の case 不在を grep で確認**、 **(b) Microsoft SMB UNIX 拡張仕様 / Samba wiki で level=513 (0x201) の本来の意味を確定**、 **(c) 次セッションへの patch 実施可否を判断** することを目的とした。 read-only 作業のみで sudo 不要、 training-tx1320 への state-changing 操作なし。

## 重要な発見 (next-session must-read)

### 🎯🎯🎯 1. **真因確定: Samba 4.19.5 の typo bug `SMB1SERVER` ≠ `WITH_SMB1SERVER`**

予想に反し、 Samba 4.19.5 には **case SMB_QUERY_POSIX_FS_INFO は存在する** (`source3/smbd/smb2_trans2.c:2532`)。 しかし、 case 内の guard 関数 `fsinfo_unix_valid_level()` (line 2018-2033) に **致命的な typo bug** がある:

```c
static bool fsinfo_unix_valid_level(connection_struct *conn,
                                    uint16_t info_level)
{
    if (conn->sconn->using_smb2 &&
            lp_smb3_unix_extensions() &&
            info_level == SMB2_FS_POSIX_INFORMATION_INTERNAL) {
        return true;
    }
#if defined(SMB1SERVER)        /* ★★★ TYPO: 正しくは WITH_SMB1SERVER ★★★ */
    if (lp_smb1_unix_extensions() &&
            info_level == SMB_QUERY_POSIX_FS_INFO) {
        return true;
    }
#endif
    return false;
}
```

- Samba の **build system は `WITH_SMB1SERVER` を define** (`wscript:421` / `source3/wscript_build:599`)
- Samba コード本体は他全箇所で **`WITH_SMB1SERVER`** (WITH_ 接頭辞付き) を使用 (例: `smb2_trans2.c:2477` の `case SMB_QUERY_CIFS_UNIX_INFO` の guard)
- **`SMB1SERVER`** (WITH_ なし) は **何処にも define されていない** (`grep -rnE 'DEFINE\(.SMB1SERVER.|#define[[:space:]]+SMB1SERVER' samba-4.19.5/` → 0 件)
- 結果: `fsinfo_unix_valid_level` は SMB1 + SMB_QUERY_POSIX_FS_INFO に対して **永久に false を返し**、 `smbd_do_qfsinfo` は `NT_STATUS_INVALID_LEVEL` を返す

これは **upstream Samba master / v4-21-stable にも同じ typo が残っている** (本セッションで WebFetch 確認)。 long-standing 未報告 bug の可能性が高い (Samba bugzilla で 0 件)。

### 🎯 2. **iRMC FW 9.08F は qfsinfo level=513 (POSIX_FS_INFO) を server capabilities 検出に使用している**

Samba wiki "UNIX Extensions" によれば `SMB_QUERY_POSIX_FS_INFO` (0x201) は statfs(2) 相当の filesystem 情報 (`FILE_SYSTEM_POSIX_INFO` 56 byte struct: OptimalTransferSize / BlockSize / TotalBlocks / BlocksAvail / UserBlocksAvail / TotalFileNodes / FreeFileNodes / FsIdentifier) を返す info level で、 UNIX 拡張の標準機能。

iRMC は VirtualMedia attach 前にこの level を要求し、 INVALID_LEVEL を受けると USB device 生成段階で abort → 60s 後に同じ sequence で retry する挙動を示す (前セッションで 8 cycle 観測)。

Samba wiki によれば本来 client は qfsinfo level=0x200 (`SMB_QUERY_CIFS_UNIX_INFO`) で capability negotiation した上で level=0x201 を発行すべきだが、 iRMC は negotiation を **skip** していきなり 0x201 を要求する。 これも仕様上不正だが、 attach のための事実上の要件として動作している。

### 🎯 3. **修正は 1 文字追加だけ — patch 案**

```diff
--- a/source3/smbd/smb2_trans2.c
+++ b/source3/smbd/smb2_trans2.c
@@ -2023,7 +2023,7 @@ static bool fsinfo_unix_valid_level(connection_struct *conn,
 			info_level == SMB2_FS_POSIX_INFORMATION_INTERNAL) {
 		return true;
 	}
-#if defined(SMB1SERVER)
+#if defined(WITH_SMB1SERVER)
 	if (lp_smb1_unix_extensions() &&
 			info_level == SMB_QUERY_POSIX_FS_INFO) {
 		return true;
```

`lp_smb1_unix_extensions()` のデフォルトは **`true`** (`source3/param/loadparm.c:724`: `Globals.smb1_unix_extensions = true;`) なので、 smb.conf に追加設定なしで patch だけで動作するはず。 既存の smb.conf に `smb1 unix extensions = no` を明示している場合のみ追加で `smb1 unix extensions = yes` が必要。

### 🎯 5. 既存 case との対比で typo bug が浮き彫り

同じファイル `smb2_trans2.c` の line 2477 で `case SMB_QUERY_CIFS_UNIX_INFO` (0x200) は **正しく `WITH_SMB1SERVER`** で gate されている:

```c
#if defined(WITH_SMB1SERVER)        /* ← 正しい */
    case SMB_QUERY_CIFS_UNIX_INFO:
    {
        ...
    }
#endif
```

一方 `fsinfo_unix_valid_level` (line 2018) だけが `SMB1SERVER` (WITH_ なし) を使用。 同じファイル内で macro 表記が **inconsistent**。 これは typo の典型パターン (誰かが `#if defined(WITH_SMB1SERVER)` を打つときに `WITH_` を打ち忘れた)。

### 6. empirical 検証 (前セッション Samba log との突き合わせ)

`report/attachment/2026-05-20_200157_tx1320_raid10_smb_n2_disproof/samba-empty-n2.log` を grep で確認:

```
[2026/05/20 17:14:39.863288] call_trans2qfsinfo: level = 513      ← smb1_trans2.c:1676
[2026/05/20 17:14:39.863310] smbd_do_qfsinfo: level = 513         ← smb2_trans2.c:2078 (関数に entry した証拠)
[2026/05/20 17:14:39.863336] NT error packet at source3/smbd/smb1_trans2.c(1686) cmd=50 (SMBtrans2) NT_STATUS_INVALID_LEVEL
                                                                   ↑ reply_nterror(req, status) の位置
                                                                   ↑ status は smbd_do_qfsinfo() が返した NT_STATUS_INVALID_LEVEL
```

`smbd_do_qfsinfo: level = 513` がロギングされた = `case SMB_QUERY_POSIX_FS_INFO` に jump した = `fsinfo_unix_valid_level()` が false を返した = case 2538 の `return NT_STATUS_INVALID_LEVEL` が実行された、 とソースコードと完全に整合する。

### 7. 副次発見: Samba master / v4-21-stable も同じ typo

upstream の最新 master および v4-21-stable でも `smb2_trans2.c` の `fsinfo_unix_valid_level` に同じ `#if defined(SMB1SERVER)` が残っている (本セッションで WebFetch 確認)。 つまり **Samba 4.19+ のあらゆる SMB1 環境で SMB_QUERY_POSIX_FS_INFO は壊れている**。 SMB1 で UNIX 拡張を本格的に使う client が稀なため気付かれずに残ったと推察。

### 8. 副次発見: Ubuntu samba 4.19.5+dfsg-4ubuntu9.4 も typo patch なし

`changelogs.ubuntu.com` で確認 (Ubuntu changelog に SMB1SERVER / fsinfo_unix の patch 言及 0 件)。 つまり ローカル Samba バイナリも upstream と同じ broken 状態。

### 2. 次セッションで考慮すべき追加リスク

- **ビルド失敗のリスク**: Samba は依存が複雑 (Heimdal, GnuTLS, LDB, Talloc, Tevent, TDB)。 Ubuntu 配置と完全一致しない可能性あり。 ABI 不一致で `/usr/sbin/smbd` 差し替えだけでは動かないことも。
- **代替手段**: 差し替えではなく `/usr/local/sbin/smbd` に install して `systemd-run --service-type=simple -p User=root -p ExecStart=/usr/local/sbin/smbd ...` で並走、 もしくは別ポートで listen
- **ABI 安全装置**: もし patched smbd の起動に失敗したら、 `sudo apt install --reinstall samba` で元に戻せる
- **smb1 unix extensions の明示**: 念のため smb.conf に `smb1 unix extensions = yes` を追加してから patched smbd を起動 (デフォルト true だが明示で確実)
- **iRMC の挙動**: patch 適用後も give-up state にあれば `Manager.Reset` が必要 (前セッション 256s 復帰観測)

| **N6-alt-2** | ksmbd (kernel SMB) で同じ share を提供 → attach 試行 | `sudo apt install ksmbd-tools`、 `/etc/ksmbd/ksmbd.conf` 設定 |
| **N6-alt-3** | Windows SMB server (Win 10/11 or Win Server) で attach 試行 | VM or 別マシン |
| N3 (継続) | iRMC OEM Licenses 確認 (本セッションでも未着手) | `GET /redfish/v1/Managers/iRMC/Oem/ts_fujitsu/iRMCConfiguration/Licenses` |
| N5 (継続) | smb_posix_open response 形式の仕様確認 | Samba ソース解析 + tcpdump |

### 4. install 完走 (本セッション未到達 — N6 step 2 成功後)

attach 成立 (patched smbd で level=513 → OK) 後、 `./scripts/tx1320-raid10-orchestrate.sh deploy` で OS install を実走。 sol-monitor で 60 分超の HW RAID10 install を monitor。

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🎯 真因は upstream Samba の 1 文字 typo bug**: 前セッション (`s-twinkly-boole`) の「level=513 は未定義」推察は誤り。 実際は SMB_QUERY_POSIX_FS_INFO (0x201) として **完全に定義 + 完全に実装** されているが、 `fsinfo_unix_valid_level` の `#if defined(SMB1SERVER)` (本来は `WITH_SMB1SERVER`) という typo により SMB1 では永久に弾かれる。 **修正は 1 文字追加のみ** で、 リスクは patched smbd の起動失敗 (rollback 可能)
2. **upstream Samba master / v4-21 でも未修正**: 本件は Samba 4.19+ のあらゆる SMB1 環境で同じ broken 状態。 つまり SMB1 で UNIX 拡張を使う client は **iRMC 以外にもほぼ存在しない** ことが裏付けられる (もし他にも使う client があれば既に bugzilla 報告されているはず)。 修正パッチを upstream に PR/メールで送る価値あり
3. **case label 不在の仮定は危険**: 前セッションは `grep 'case 513'` を smb1_trans2.c だけで実施 → 0 件 → 「未定義」と推論。 本セッションでは smb2_trans2.c (実装が SMB1/SMB2 共通) まで広げて確認したことで真因に到達。 **次回は最初から `source3/` 全体 + ヘッダ含めて grep する**
4. **`grep NT_STATUS` で non-OK を全件確認する習慣を継続**: 前セッションで INVALID_LEVEL を発見したこの手法は引き続き有効。 N6 step 2 の検証時も同じ手法で patched smbd の挙動を確認できる
5. **iRMC は CIFS UNIX capability negotiation を skip する**: 仕様上は qfsinfo level=0x200 で negotiation してから 0x201 を発行すべきだが、 iRMC FW 9.08F は直接 0x201 を要求する。 patch 後にこれで動作する保証はないが、 N6 step 2 で patched smbd が level=513 に正規 response を返せば、 iRMC 側で USB device 生成に進む可能性が高い (前セッションの give-up タイミングからの推察)
6. **lp_smb1_unix_extensions() のデフォルトは true**: `source3/param/loadparm.c:724` で `Globals.smb1_unix_extensions = true;`。 patch 適用後 smb.conf に明示設定なしでも動作するはず
7. **次セッションで Samba をフルビルドする際は Ubuntu の dpkg 配置に揃える `--libdir=/usr/lib/x86_64-linux-gnu` を必ず指定**。 これを忘れると共有ライブラリの location ずれで起動失敗
8. **rollback 手段は明確**: バックアップ smbd 差し戻し or `apt install --reinstall samba` で常時復元可能
