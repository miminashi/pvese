## 前提・目的

前セッション (s-expressive-bubble) で silent failure の真因が **iRMC FW 9.08F の SMB redirector が file open + AIO read 後に USB device を生成しない** ことまで packet レベル + Samba application log で確定。 60秒間隔の retry サイクル + 数時間連続失敗で give-up state も観測。 ネットワーク経路品質は無罪。 未検証だった新仮説 **N1** = `trans2 setpathinfo (info_level=521 / SMB_SET_FILE_UNIX_BASIC = chmod 試行) が EPERM で iRMC abort` を、 ISO `chown nobody:nogroup` + smb.conf `[public] force user = nobody` で対策して検証することが本セッションの目的。 確定すれば本セッション内で deploy + install まで完走 (Issue #69 close 想定)、 反証なら NT_STATUS を必ず記録して N2/N3 を次セッションへ持ち越す。

## 重要な発見 (next-session must-read)

### 🎯 1. **N1 反証確定**: setpathinfo + posix_open はそもそも NT_STATUS_OK で成功している

Phase 2 で N1 の対策 (ISO chown nobody:nogroup + smb.conf `force user=nobody / force group=nogroup`) を適用した状態で ConnectCD trigger、 120s polling の結果:

| 観測 | 値 |
|------|-----|
| Members.count 24 iter (120s) すべて | **0** |
| AllowableValues に `DisconnectCD` 出現 | **なし** |
| iRMC give-up state | **解除済** (Phase 1 Manager.Reset 後、 Samba session 確立) |
| Samba 側の effective uid | 65534 (nobody) ★ force user=nobody が確実に効いている ★ |
| setpathinfo `info_level=521` | NT_STATUS_OK |
| smb_posix_open mode 0755 | NT_STATUS_OK |
| smbXsrv_open_global_store status | NT_STATUS_OK |
| smbd_check_access_rights_sd (access_mask 0x89) | NT_STATUS_OK |
| g_lock_lock | NT_STATUS_OK / WAS_UNLOCKED |
| 60秒 retry サイクル | **継続** (14:37:23 / 14:38:24 / 14:39:25 / 14:40:26 で 4 回観測) |

decisive evidence (samba-empty-n1.log:208-319):

```
14:37:23.862249 Impersonated user: uid=(65534,65534), gid=(0,65534), cwd=[/var/samba/public]
14:37:23.862283 call_trans2setpathinfo: fname=debian-training-tx1320-raid10.iso info_level=521 totdata=18
14:37:23.862571 smb_posix_open: file debian-training-tx1320-raid10.iso, smb_posix_flags=1024, mode 0755
14:37:23.862590 create_file_default: access_mask=0x89 ... create_disposition=0x1 ... fname=debian-training-tx1320-raid10.iso
14:37:23.862716 smbXsrv_open_global_store: key '4ADFB099' stored
14:37:23.863098 smbXsrv_open_create: global_id (0x4adfb099) stored
                status                   : NT_STATUS_OK
```

つまり Samba 側はすべて success で、 **setpathinfo の chmod は EPERM では落ちていなかった**。 N1 仮説は反証。 真因は別所。

### 🎯 2. **force user=nobody の副作用**: iRMC は AIO read を発行せず ~320ms 後に即 SMBclose

最も重要な変化点。 前セッション (root:root 0644 / force user 設定なし) では setpathinfo 後に AIO read (`schedule_aio_read_and_X` + `aio_pread_smb1_done`) まで観測されたが、 **本セッション (chown nobody + force user=nobody) では AIO read 自体が来ない**:

| 時刻 | イベント |
|------|---------|
| 14:37:23.862283 | call_trans2setpathinfo |
| 14:37:23.862571 | smb_posix_open NT_STATUS_OK |
| 14:37:23.863098 | smbXsrv_open_create NT_STATUS_OK |
| 14:37:24.182342 (~**320ms** later) | **SMBclose** (reply_close fd=30 fnum 49709) |
| 14:38:24.661478 (+60s) | retry: call_trans2setpathinfo (同上シーケンス) |

`grep -E 'aio|pread|reply_read' tmp/329269dc/samba-*n1.log` の結果は **0 件**。 SMBread / read_and_X / aio_pread 一切なし。 iRMC は setpathinfo + posix_open + smbXsrv_open_create 成立後に **read を 1 packet も発行せずに直ちに close** している。

考えられる説明:
- iRMC は SMB UNIX 拡張の open 直後に何らかの metadata 取得 (例: getattr / file size) を期待しているが、 force user=nobody 環境では他の qpathinfo 系コマンドの response 形式が違うため abort
- iRMC は POSIX OPEN response の何かのフィールド (例: file_id, end_of_file) が想定値と違うため abort
- force user=nobody 適用後、 Samba は uid を即 nobody に固定し、 iRMC は session setup 後の guest user 帰属の mismatch (smbXsrv_open_global の `open_owner: S-1-22-1-65534` = SID for uid 65534) を見て abort

### 🎯 3. **60秒 retry サイクルは本セッションでも継続**: 真因の本質は変わらず

setpathinfo + posix_open + smbXsrv_open_create + ~320ms 後 close → 60s 沈黙 → 同じシーケンス retry。 これを 120s 中に 4 回観測 (14:37:23 / 14:38:24 / 14:39:25 / 14:40:26)。 つまり N1 修正は「iRMC が何で abort しているかの phase をズラした」だけで本質的解決には至らず。

### 🎯 4. iRMC give-up state は数時間放置で自然解除する

前セッション末 (2026-05-19 16:38) から本セッション開始 (14:25 起算) まで約 22 時間放置。 Phase 1 で Manager.Reset を実施したが、 仮に Reset せずに直接 ConnectCD したとしても SMB session 確立できる状態だった可能性が高い (Samba session log は Phase 2 で正常な NTLMSSP → tree connect → setpathinfo まで確認)。 ただし運用上は Manager.Reset を冒頭で実施する方が確実 (本セッションでは 105 秒で復帰、 ServiceTemporarilyUnavailable 期間 ~30s)。

### 🎯 5. iRMC が試みる SMB シーケンスの完全像 (本セッションで確定)

```
ConnectCD POST (HTTP 204)
↓
TCP 3way → port 47642
↓
SMB1 Negotiate (NT LM 0.12)
↓
SMB1 Session setup: NTLMSSP + UserName=guest
  → guest が Samba passdb に無し → NT_STATUS_NO_SUCH_USER
  → `map to guest = bad user` で nobody (uid 65534) フォールバック
  → NT_STATUS_OK
↓
SMB1 Tree connect: \\10.1.6.1\public → NT_STATUS_OK
↓
SMB1 Trans2 SETPATHINFO info_level=521 (SET_FILE_UNIX_BASIC), totdata=18 → NT_STATUS_OK
↓
SMB1 Trans2 SMB_POSIX_OPEN mode=0755, flags=1024 → NT_STATUS_OK (open_global_id=0x4adfb099)
↓
[★ 本セッションで N1 修正後の変化点 ★]
  前セッション: schedule_aio_read_and_X → aio_pread_smb1_done → 60s 沈黙
  本セッション: read 一切なし → ~320ms 後 SMBclose → 60s 沈黙
↓
60s 後、 上記シーケンス全体が retry (同じ pid 4000687、 異なる fnum / open_global_id)
↓
4 回 retry を観測後、 Members.count=0 維持で polling timeout (120s)
```

## 重要な教訓 (次セッションへの引き継ぎ)

1. **N1 仮説 (setpathinfo EPERM) は実は反証されていた**: 前セッションは setpathinfo の NT_STATUS まで詳細に解析していなかった。 setpathinfo が呼ばれる事実だけ確認していた。 本セッションで `log level = 10` 下で setpathinfo + posix_open + smbXsrv_open_create を一連で確認し、 すべて NT_STATUS_OK と判明。 chmod は元から成功していた。 **仮説検証時は仮説の証拠ポイントを Samba log で個別に grep して NT_STATUS まで確認すること** (前セッションは smb_posix_open の存在しか確認していなかった)
2. **force user=nobody の副作用**: 単純に「effective uid を 65534 に固定する」だけと思いきや、 iRMC SMB client は force user 適用後の Samba response (おそらく smb_posix_open response 内のフィールド) を「ない」と判断して AIO read を発行せず即 SMBclose する。 これは予想外の副作用で、 N1 検証以外に影響を与える可能性あり。 **次セッションで N2/N4 検証時は force user 設定なしに戻すこと** (本セッションで Phase 5 で復元済)
3. **iRMC give-up state は数時間で自然解除する**: 前セッション末 22 時間後の本セッション開始時点で Manager.Reset 前から Samba session 確立は可能と推察される (Phase 2 で TCP/SMB negotiate/setpathinfo まで正常)。 give-up state 解除のために Manager.Reset を急ぐ必要はないが、 デバッグ作業冒頭の安全確保として実施するのは依然有効
4. **`/var/log/samba/log.` (空 %m) の存在を忘れない**: 前セッションの教訓だが、 本セッションでも同じ。 trans2 系 (setpathinfo, posix_open, AIO) はすべて空 %m ログに書かれる。 per-machine ログには NTLMSSP 認証往復のみ。 ログ取得時は **両方** 必ず capture
5. **N1 反証の意味**: 真因は「iRMC は file open 後の何か特定の操作 (read or response field validation) で abort する」に絞られる。 force user=nobody で AIO read を発行しなくなった事実は、 「AIO read の有無」と「USB device 生成の有無」が独立していることを示す (どちらの場合も USB device 生成されず)。 つまり真因はもっと上流 (open response の何かのフィールド評価) にある可能性が高い
6. **smb.conf 変更時の互換性保護**: 本セッションでも backup → 適用 → 復元 → diff 0 + smbclient -L baseline 比較で完全保護。 sudo 操作はすべて `! sudo sh tmp/<sid>/<phaseN>.sh` で依頼するパターンが有効。 1 スクリプト = 1 phase = 1 sudo prompt で運用負荷少なめ
7. **ping baseline は 226ms / 0% loss で前 3 セッションと同水準**: 経路品質は安定。 次セッションでも ping precheck で大幅悪化がなければ即 N2/N4 検証に進んで OK
