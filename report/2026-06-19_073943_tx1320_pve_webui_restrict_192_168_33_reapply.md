## 前提・目的

2026-06-14 に実施した pveproxy アクセス制限 ([旧レポート](2026-06-14_022710_tx1320_pve_webui_restrict_192_168_33.md))
を、現在の training-tx1320 に**再度**適用する。

- **背景 / 再適用が必要な理由**: ホストは 2026-06-19 にブリッジ構成 (vmbr0=eno1 LAN / vmbr1=eno2
  dark-net 固定 10.1.4.16) で **RAID 初期化からフルセットアップし直された**
  ([ブリッジ構成レポート](2026-06-19_045707_tx1320_pve_bridge_vmbr0_lan_vmbr1_darknet.md))。
  再インストールにより `/etc/default/pveproxy` はリセットされ、適用前は**未存在 = アクセス制限なし**の状態だった。
- **目的**: PVE Web UI + REST API (= 同一の `pveproxy` TCP 8006) を **127.0.0.1 (loopback) +
  192.168.33.0/24** のみ許可し、それ以外 (dark-net 10.0.0.0/8 / 10.1.4.16 含む) を遮断する。SSH (22) は維持。
- **ユーザ確定事項**:
  - 対象 = Web UI + API (= pveproxy 8006)、SSH は開けたまま
  - 許可元 = 127.0.0.1 + 192.168.33.0/24、それ以外は全拒否
  - 機構 = `/etc/default/pveproxy` の ALLOW_FROM/DENY_FROM/POLICY (PVE 公式機構。firewall/iptables は使わない)
  - 適用範囲 = **現ホストのみ** (リポジトリのスクリプト/設定は無改変)、冪等に

### 重要な前提

- PVE の **Web UI と REST API は同一の `pveproxy` (TCP 8006)** で提供される。8006 を絞れば両方が同時に制限される。
- SSH (22) は pveproxy と別系統 (sshd) のため、pveproxy のアクセス制限・再起動の影響を受けない (= 復旧経路として残る)。
- **ブリッジ構成下でも source-IP ベースの制限は意図どおり効く**: pveproxy はユーザ空間プロキシで `*:8006` を
  bind し、TCP peer (送信元) IP を素で参照する。PVE ホスト上で incoming に NAT は介在しない (ブリッジは L2) ため
  送信元 IP が保存される。

## 実施内容

`/etc/default/pveproxy` を冪等に設定 (適用前は未存在のため実質新規作成)。最終内容:

```
ALLOW_FROM="127.0.0.1,192.168.33.0/24"
DENY_FROM="all"
POLICY="allow"
```

`POLICY="allow"` 下で `DENY_FROM="all"` が全拒否しつつ `ALLOW_FROM` 一致を許可する (ALLOW が DENY に優先)。
結果として 127.0.0.1 と 192.168.33.0/24 のみ許可され、それ以外 (dark-net 含む) は接続段階で拒否される。

冪等性の担保: 適用スクリプト (`tmp/edd0e096/apply-pveproxy.sh`) は、既存ファイル (無ければ空) から
`^[[:space:]]*(ALLOW_FROM|DENY_FROM|POLICY)=` にマッチする行を一括除去 → 正準 3 行を追記 → 一時ファイルを
`/etc/default/pveproxy` へアトミックに `mv` する。これにより初期状態 (不在 / 3 キーあり / 一部キーのみ /
無関係キー併存) に関わらず、実行後は常に「各キー 1 行ずつ + 無関係行は保存」に収束する (再実行で重複しない)。

適用後 `systemctl restart pveproxy` を実行 (→ active)。CLAUDE.md 規則によりラッパーを `scp` → `ssh sh` で実行し、
ローカルの操作ログは `./oplog.sh` で記録した。

## 検証結果

| テスト | 送信元 | 適用前 | 適用後 | 判定 |
|--------|--------|--------|--------|------|
| Web UI (`https://:8006/`) | claude (→10.1.4.16) | 200 | 接続不可 (000) | ✅ 遮断 |
| API (`/api2/json/version`) | claude (→10.1.4.16) | 401 (認証要求 = 到達) | 接続不可 (000) | ✅ 遮断 |
| Web UI | loopback 127.0.0.1 (ホスト上) | 200 | 200 | ✅ 許可 |
| Web UI | vmbr0 192.168.33.11 (ホスト上) | 200 | 200 | ✅ 許可 |
| Web UI | vmbr1 自己 10.1.4.16 dark-net (ホスト上) | 200 | 接続不可 (000) | ✅ 遮断 |
| SSH (22) | claude → 10.1.4.16 | OK | OK | ✅ 維持 |
| pveproxy サービス | — | active | active | ✅ 稼働 |

- 適用前の全値は本作業の冒頭で実機取得済 (claude 200/401、ホスト lo/vmbr0/vmbr1 = 200/200/200)。
- pveproxy は不許可 IP を **TLS 接続確立前に切断** する挙動 (curl exit 35 / http_code 000)。403 を返すより
  手前で弾くため、より強い遮断となっている (本セッションは claude→IPv4 で exit 35 を確認。IPv6 は未検証)。
- API の適用前 401 は「認証トークン未指定だが pveproxy には到達している」状態。適用後は送信元 IP に基づき
  TLS 層で切断 (000) されるため、Web UI と同様に遮断成立を確認。
- **SSH 維持の立証**: pveproxy restart 後にホスト側検証スクリプトを `ssh` 経由で実行できた事実そのものが、
  restart が SSH に影響しないことの実機証拠 (sshd と pveproxy は独立系統)。

## 再現方法

1. tx1320 へ到達 (固定管理 IP):
   ```sh
   ping -c2 10.1.4.16
   ssh -F ssh/config training-tx1320   # = root@10.1.4.16
   ```

2. `/etc/default/pveproxy` を冪等に設定 (既存の同名キーを除去してから追記):
   ```
   ALLOW_FROM="127.0.0.1,192.168.33.0/24"
   DENY_FROM="all"
   POLICY="allow"
   ```
   ※ パイプ/リダイレクトを含むため、ラッパースクリプトを `scp` → `ssh sh /tmp/apply-pveproxy.sh` で実行する
   (CLAUDE.md パーミッション規則。インライン禁止)。

3. pveproxy 再起動:
   ```sh
   systemctl restart pveproxy
   systemctl is-active pveproxy
   ```

4. 検証:
   ```sh
   # claude 側 (ローカル) → 接続不可 (000) になること
   curl -sk -o /dev/null -w '%{http_code}\n' --connect-timeout 8 https://10.1.4.16:8006/
   # ホスト上 loopback / vmbr0 → 200、vmbr1 自己 → 000 になること (ssh 経由でホスト上で実行)
   curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8006/
   curl -sk -o /dev/null -w '%{http_code}\n' https://192.168.33.11:8006/
   curl -sk -o /dev/null -w '%{http_code}\n' https://10.1.4.16:8006/
   ```

## 復旧手順

`/etc/default/pveproxy` は今回新規作成したため、制限を完全に解除するには
`rm /etc/default/pveproxy && systemctl restart pveproxy` を実行すればよい (デフォルトの全許可動作に戻る)。
SSH は遮断していないため、いつでも復旧操作が可能。

## 補足・発見事項

- ユーザ指定により **リポジトリのスクリプト/設定は変更していない** (現ホストのみ適用)。
  tx1320 を再インストールするとこの設定はリセットされる (今回がその再発生ケース)。
- **ブリッジ構成下での差分 (今回の固有点)**:
  - claude の到達 IP が固定 **10.1.4.16** (vmbr1 static) になった。許可元は不変のため適用内容は前回と同一。
  - claude ホストの送信元 IP は dark-net 側 (`10.1.x`) で 192.168.33.0/24 外のため、**適用後は claude 自身が
    web UI / REST API を失い、SSH (22) のみが残る**。これは仕様 (許可元限定) の意図的な帰結。
  - ホストが自分の `vmbr1` アドレス (10.1.4.16) を叩く自己接続も遮断される (送信元 = dark-net IP)。一方
    `vmbr0` (192.168.33.11) の自己接続は許可レンジ内のため 200。
- **適用前は完全に未制限だったことを実機確認**: `/etc/default/pveproxy` 不在 + pve-firewall disabled +
  iptables に 8006 ルールなし + listen `*:8006`。8006 を絞る他機構は存在しなかった。
- **IPv6 の扱い**: pveproxy は `*:8006` で dual-stack listen する (本セッションで `ss` により確認済)。
  `ALLOW_FROM` は IPv4 のみを列挙するため `::1` を含む全 IPv6 送信元は拒否される
  (この `::1` 遮断は[前回レポート](2026-06-14_022710_tx1320_pve_webui_restrict_192_168_33.md)で
  `https://[::1]:8006/` → 000 を実機確認済。**本セッションでは IPv6 を再検証していない**)。
  ホストローカル通信は 127.0.0.1 経由のため実害は低い (`::1` で 8006 を叩くツールがある場合のみ
  `ALLOW_FROM` に `::1` 追加が必要)。
