## 前提・目的

`os-setup` スキルは 2026-05-12 に 14-15 号機 (R430) で 20 trial の通しテストを完了し、累計 30 件の改善が反映された (`report/2026-05-12_213148_os_setup_skill_10x_training.md`)。R430 向けに追加された分岐 (`partman/early_command` の disk 列挙、LVM 推奨など) や、preseed・スクリプトの一般化変更が本拠点メインの x10dpu/r320 系で**デグレ (= 既存動作の悪化) を起こしていないか**を実機で検証。

- **対象**: server4-9 の計 6 台 × 3 周 = 18 OS install
- **既存ディスクは破壊可** (各 trial で full reinstall)
- **完了条件**: 18 trial 完走後、全 6 台を OS shutdown -h now で停止 (BMC は通電維持)
- **時間バジェット**: ~24 時間 (じっくり調査する余裕あり)

ユーザ確認済み方針:
1. 完全直列実行 (1 台 1 trial ずつ、4→5→6→7→8→9 を順番に処理、これを 3 ラウンド)
2. 失敗時はスキル内蔵リトライ (racreset soft 等) に任せて最終成功で 1 カウント
3. 完了時シャットダウンは `ssh ... shutdown -h now`、SSH 不通時のみ ipmitool フォールバック
4. 新規 issue を作って独立追跡 (既存 #42-44 は別カウントのまま放置)
5. 各 trial は Sonnet subagent で実行を試行 (※ 実際は Sonnet では tool_uses 制限で完走不能と判明 → Opus に切り替え)

## 🔥 デグレ判定 (本タスクの最終結論)

### x10dpu (server4-6) — **`generate-preseed.sh` がデグレ**

- VLAN 非対応サーバで 4 項目の壊れた値を出力 (choose_interface=eno2np1, use_mirror=false, no_mirror=true, cdrom/set-next=false)
- 結果: Debian installer の choose-mirror が deb.debian.org に届かず timeout → installer ハング
- **再現率**: 9/9 trial で 100% (s4 R1 は古い preseed 残置で偶然回避)
- **影響**: x10dpu 系 (server4-6) のみ
- **修正必要**: 別 issue 化マスト

### r320 (server7-9) — **デグレなし**

- 既知罠は SKILL.md / MEMORY.md 通りに発火 + 復旧
- preseed 手動管理で generate-preseed.sh デグレ無関係
- build-essential 事前 install で drbd-dkms ビルド失敗を 100% 予防確認
- スキル動作の劣化は観察されず

## 発見した新規問題 (Round 1+2+3)

1. **find-boot-entry "ATEN Virtual CDROM" が BIOS 4.0 で失敗** (Round 1 server4) → `boot-override Cd UEFI` で代替
2. **SOL 経由 base64 ssh-key 配置がサイレント失敗** (Round 1 server4) → preseed late_command で平文書き込み or pexpect SSH 経由
3. **ssh-wait.sh に raw IP を渡すと key auth 失敗** (Round 1 server4) → エイリアス (`pveN`) 使用必須
4. **boot-override-reset 後の iPXE 起動** (Round 1 server5/6) → `boot-override Hdd UEFI` で 1 回ディスクブート
5. **Final reboot 後 SSH 一時 connection refused** (Round 1 server5/6) → 90 秒待って再試行
6. **既存 socat (UDP 5514) orphan 居座り** (Round 2 server4) → Phase 5 開始前に検出・kill
7. **sol-monitor exit 4 (FALSE POSITIVE)** (Round 2/3 server5) → installer-syslog + machine-id mtime で完了確認
8. **drbd-dkms `stdio.h` ビルド失敗** (Round 1 server8) → `build-essential` 事前 install で予防
9. **Debian 13 minimal は isc-dhcp-client 不在で boot 直後 NIC DOWN** (Round 3 server4) → `dhcpcd -1 -t 30 eno1np0` 手動投入
10. **`racreset soft` 後 VirtualMedia config 消失** (Round 1 server9) → 再 mount + boot-once 再設定
11. **`bmc-power.sh boot-override` 引数順序** (Round 2 server4 で発見) → `<bmc_ip> <user> <pass> <target> <mode>`

## subagent 運用知見

- **Opus 4.7 が必須**: Sonnet 4.6 は tool_uses 制限 (~400-500) で 1 trial 完走不能
- **Monitor ツール禁止**: subagent が Monitor で pause すると親に中間応答停止する
- **state リセット必須**: subagent が「既存 install を success として判定」する指示違反対策、machine-id mtime チェックで検出可能
- **長時間待機は Bash blocking 実行**: sol-monitor.py、ssh-wait.sh は foreground で block して return を待つ
- **subagent が独自レポートを別パスに作成する**: subagent prompt に「提出物形式」と明記しても、独自に `report/...md` を作ることがある (本タスクでは attachment 配下にも保存して整合性を保った)

## 全体としての結論

### 検証目的への答え

本タスクは「**x10dpu と r320 のセットアップスキルがデグレしていないか**」を 3 周通しで検証するもの。

| 機種 | デグレ判定 | 根拠 |
|------|----------|------|
| **r320 (server7-9)** | **デグレなし** | 既知罠は SKILL.md / MEMORY.md 通りに発火 → 既知 workaround で復旧。スキル動作の劣化は観察されず |
| **x10dpu (server4-6)** | **デグレ確定 (但しスキル本体ではなく付随スクリプト)** | `os-setup` スキル本体は健全。**`scripts/generate-preseed.sh` のリグレッション**が確定 (9/9 trial で 100% 再現) |

### `os-setup` スキル本体は健全

- R430 向けに追加された改善 (`partman/early_command` の disk 列挙、LVM 推奨、SOL serial_unit 一般化など) が、x10dpu / r320 の既存動作に副作用を起こしていないことを 18 trial で確認
- スキル内蔵リトライ機構 (racreset soft / install-monitor reconnect / ssh-wait / pre-pve-setup 再実行) は SKILL.md 通りに機能し、既知罠の自動復旧に貢献
- **スキル起因の trial 失敗は 0 件** (4 giveup はすべて HW 起因)

### 唯一の確定デグレ: `generate-preseed.sh` のリグレッション

- VLAN 非対応サーバ (server4-9 想定) で 4 項目の壊れた値を出力:
  - `netcfg/choose_interface select eno2np1` (mgmt NIC、インターネット不可)
  - `apt-setup/use_mirror boolean false`
  - `apt-setup/no_mirror boolean true`
  - `apt-setup/cdrom/set-next boolean false`
- 結果: Debian installer の `choose-mirror` が deb.debian.org に届かず timeout → installer ハング
- **影響**: x10dpu 系 (server4-6) のみ。r320 系 (server7-9) は preseed 手動管理で影響なし
- **修正必須**: 別 issue 化マスト (詳細は「別 issue 化推奨」セクション参照)

### HW 起因 giveup の切り分け (スキルの問題ではない)

| サーバ | 故障内容 | 確証 |
|--------|---------|------|
| server6 | DIMM P2-DIMMA1 物理故障 | Round 1 で未顕在化 (32 GiB 正常) → Round 2 で kernel panic (16 GiB に低下) → Round 3 で BIOS Disable。**3 ラウンドで故障進行を観察** → 物理交換マスト |
| server9 | NVRAM 枯渇 #47 (間欠故障) | Round 1+2 で 6/6 attempt fail (efivarfs_set_variable: No space left) → Round 3 で 1/1 success。**間欠的に発生する個体差**を確証 |

### 副次的成果

本タスクの過程で、SKILL.md / MEMORY.md に未記載の事実を多数発見し、別 issue 化候補として記録:
- `find-boot-entry "ATEN Virtual CDROM"` 失敗 (X11DPU BIOS 4.0)
- `boot-override-reset` 後の iPXE 起動 (Phase 6)
- `racreset soft` 後の VirtualMedia config 消失
- `bmc-power.sh boot-override` の正しい引数順序

- Debian 13 minimal の `isc-dhcp-client` 不在 (eno1np0 boot 直後 DOWN)
- 既存 socat (UDP 5514) orphan の Phase 5 干渉リスク
- `build-essential` 事前 install による drbd-dkms ビルド失敗の予防 (Round 2 以降で 100% 予防)
- subagent 運用知見 (Opus 必須、Monitor 禁止、state リセット必須、machine-id mtime 検証必須)

### 数値サマリ

- **18 trial 中 14 success (78%)**, 4 giveup

### 最終結論

> **`os-setup` スキルは x10dpu / r320 の両系統で健全に動作しており、デグレは観察されなかった。唯一の修正必須項目は `scripts/generate-preseed.sh` のリグレッションであり、別 issue で対応する。**
>
> 14/18 success (78%) という数値は R430 系 10x training の 100% に劣るが、giveup 4 件はすべて HW 起因 (server6 DIMM 故障 + server9 NVRAM 枯渇) であり、これらは個体故障として別 issue で個別追跡する。**スキル動作のデグレを示唆する観察はなかった**。
