## 前提・目的

- **背景**: TX1320 の OS install は Phase 19 (2026-05-30, commit `dbb936a`) で **PXE pivot** により完遂済み。iRMC USB redirector の累積劣化 (FW 9.69F でも BIOS POST 99 stuck) を回避する経路として `pxe-deploy` skill が確立した。ただし Phase 19 は 1 回成功の実績のみで、**反復実行時の堅牢性・再現性は未検証**だった。
- **目的**: 確立済み PXE 経路を **10 回連続反復**し、(1) 再現性 (成功率)、(2) 所要時間の分布、(3) 失敗モードとリトライ要否、(4) 新たな落とし穴を洗い出し、各回の知見を `pxe-deploy` SKILL.md に蓄積する。
- **成功基準**: 各回 install 完遂 → disk boot → eno2 dark-net IP 特定 → SSH login + RAID10 Optimal 検証 (= SSH 到達まで)。
- **方針**: ネットワーク関連操作の失敗は最大 3 回まで再試行。インフラ起因のブロッカーはユーザに依頼せず自力復旧して継続。

参照: [Phase 19 PXE pivot 完遂レポート](2026-05-30_050830_tx1320_raid10_phase19_pxe_autonomous_ssh.md)、[Phase 1-19 総括](2026-05-30_053607_tx1320_raid10_overview_phase1-19_summary.md)

## 再現方法

実 install は sonnet エージェント (`general-purpose`, `model: sonnet`) に逐次移譲。1 回分のシーケンス (Step 0–9):

```sh
# 共有セットアップ (初回のみ): session-id 確定 + tmp/<sid>/ 作成 + ヘルパー生成 + フル preflight

# Step 0: preseed 生成 + playground 配置 (disconnect-cd は FW 9.69F で 400 → スキップ)
./scripts/generate-preseed.sh --pxe=http://10.1.6.6 config/training_tx1320.yml tmp/<sid>/training-tx1320.cfg
./oplog.sh sh tmp/<sid>/deploy-preseed.sh   # scp + cp で /var/www/html/preseed/training-tx1320.cfg へ

# Step 1-3: ForceOff → boot-override Pxe UEFI → PowerOn
./oplog.sh ./scripts/bmc-power.sh forceoff 10.254.254.9 claude Claude123
./oplog.sh sh tmp/<sid>/boot-pxe.sh    # 直接 curl PATCH (bmc-power.sh の -L bug 回避)
./oplog.sh ./scripts/bmc-power.sh on 10.254.254.9 claude Claude123

# Step 4-5: 監視 + 完遂判定 (真の進捗 = nginx access.log の preseed/storcli/phonehome GET + OEM screenshot)
./oplog.sh .venv/bin/python scripts/sol-monitor.py --bmc-ip 10.254.254.9 --bmc-user claude --bmc-pass Claude123 --log-file tmp/<sid>/install-N.log --timeout 3000 --powerstate-interval 30
# 完遂 = sol-monitor rc=0 + PowerState Off + nginx に phonehome GET

# Step 6-7: boot-override Hdd UEFI → PowerOn (disk boot)
./oplog.sh sh tmp/<sid>/boot-hdd.sh
./oplog.sh ./scripts/bmc-power.sh on 10.254.254.9 claude Claude123

# Step 8-9: eno2 IP 特定 (ip neigh) → SSH + RAID10 検証
sh tmp/<sid>/find-ip.sh    # ip neigh | grep 4c:52:62:14:de:f0
scp -F ssh/config tmp/<sid>/verify-raid.sh root@<eno2-IP>:/tmp/verify-raid.sh
ssh -F ssh/config -i ssh/id_ed25519 root@<eno2-IP> "sh /tmp/verify-raid.sh"
# storcli64 /c0/vall show → RAID10 Optl 1.635 TB + 4 drives Onln + lsblk sda 1.6T
```

リトライ規約: ネットワーク操作 (DHCP / kernel fetch / preseed fetch / scp / ssh / IP 特定 / SSH 到達 / bmc Redfish) は各最大 3 回。iPXE が converge しない時は power cycle 最大 3 回。install 本体失敗は Step 1 から最大 3 回再 install。冪等性は `setup-raid10-storcli.sh` の `/c0/vall delete force`→RAID10 再作成で担保 (各回前回状態に非依存)。

### 判明した新たな落とし穴 (SKILL.md に #10–15 として記録済み)

| # | 現象 | 真因 | 対策 |
|---|------|------|------|
| 10 | `bmc-power.sh boot-override` rc=52 | `redfish_patch` の `curl -skL` の `-L` (follow redirect) が PATCH と競合し empty reply | boot-pxe.sh/boot-hdd.sh で直接 `curl -sk` (no `-L`) PATCH。または bmc-power.sh から `-L` 削除 |
| 11 | `irmc-virtualmedia.sh disconnect-cd` が 400 | iRMC FW 9.69F で OEM action 名変更 | PXE 経路では Virtual Media inactive のため**スキップ可** |
| 12 | eno2 DHCP IP が毎回変動 | dark-net DHCP はリース固定なし | IP は毎回 `ip neigh \| grep 4c:52:62:14:de:f0` で特定 |
| 13 | `ssh root@<eno2-IP>` が Permission denied | ssh/config の固定 Host が動的 IP にマッチせず IdentityFile 不適用 | `ssh -i ssh/id_ed25519` 明示、または `Host 10.254.254.*` ワイルドカード追加 (対応済) |
| 14 | disk boot 後 eno2 DHCP が 15min 以上遅延 (確率的、Run 3) | `allow-hotplug eno2` がリンクアップイベント検出後に DHCP 開始。ケーブル既接続で初回イベント不発生のことがある | ARP 未出現時は brute-ping / arp-scan で特定。最大 15–20min 待機 |
| 15 | **(主要失敗モード, 30%)** 初回 attempt で preseed GET が来ず d-i がスタック | eno2 link-up が d-i netcfg 中に発生 → 2 NIC 分の IPv6 autoconfiguration タイムアウトが累積、または eno2 (gateway なし) 先行取得で「Name server addresses:」interactive dialog に陥る。非決定的 | preseed GET が ~10–15min 来なければ **ForceOff → retry**。2 回目は通常 +3m30s で preseed GET (即時解消) |

### 副次的な観察

- **SOL monitor の誤完了判定**: 手動 ForceOff 後に sol-monitor が PowerState=Off を検出して rc=0 "Installation completed" と誤報告することがある。**完遂判定は必ず nginx の phonehome GET の有無で確認**すること (PowerState 単独で判断しない)。本検証ではこのガードにより誤判定なし。
- **真の進捗指標**: SOL stage 検出は ring buffer replay で誤検出する。nginx access.log の preseed→storcli64.bin→phonehome GET の順序と OEM screenshot が信頼できる一次情報。

## 結論

- PXE 経路 (`pxe-deploy` skill) は **10 回全成功・再現性 100%**。USB redirector 累積劣化に依存しないため、Phase 1–18 の Virtual Media 経路と異なり安定して反復可能。
- **インフラ層 (BMC Redfish / OpenWrt TFTP / playground nginx / mirror) は NW retry 0 回**で極めて安定。
- 唯一の有意な失敗モードは **落とし穴 #15 (d-i dual-NIC netcfg stuck, 発生率 30%)**。ForceOff+retry で即座に回避できるため実用上のブロッカーにはならないが、**無人運用の信頼性向上には preseed/cmdline での恒久対策が望ましい** (下記フォローアップ)。
- install 本体の所要時間は安定して ~11–12min。SSH 到達までの総時間 (13–26min) の主な変動要因は eno2 DHCP 取得時間 (#14) と #15 の retry。

### フォローアップ候補 (本タスク範囲外・未実施)

1. **#15 恒久対策**: preseed で install 用 NIC を明示固定 (`netcfg/choose_interface`) する、または d-i 起動時に eno2 を down させて単一 NIC で netcfg を通す、`netcfg/get_nameservers` を preset して DNS dialog を抑止する。これにより 30% の retry を排除できる見込み。
2. **#10 恒久対策**: `scripts/bmc-power.sh` の `redfish_patch` から PATCH 時の `-L` を外す (boot-override を bmc-power.sh 単体で動かせるようにする)。
3. **#14 緩和**: installed-system の eno2 を `auto` + `dhcp` (allow-hotplug でなく) に変更し、起動時 DHCP を確実化。
