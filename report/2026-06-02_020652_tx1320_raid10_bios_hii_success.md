## 前提・目的

- **背景**: RAID コントローラ PRAID EP400i (LSI MegaRAID SAS3008) は RAID10 を確実にサポートする（RAID5/6 が作成できる以上 RAID10 も可能）。一方で BIOS HII KVM 経由の RAID10 作成は 2026-05-17 に「Select RAID Level 到達不可」で dead-end と判定されていた。
- **目的**: 公式マニュアル・Web 情報を十分調査した上で、BIOS RAID 設定から RAID10 を構築できるか実機で再検証する。
- **ユーザ確定事項**: HII が「やはり不可」と一次根拠付きで確定した場合はそこで停止（OEM Redfish / storcli 等のフォールバックには進まない）。

## 環境情報

- 機体: Fujitsu PRIMERGY TX1320 M3 / Mainboard D3373 (S26361-D3373-B12) / 24 GiB RAM / Serial MABK035229
- BMC: iRMC S4 FW **9.69F** / SDR 3.18 / BIOS V5.0.0.11 R1.22.0 (Aptio Setup Utility 2.18.1263)
- RAID コントローラ: **PRAID EP400i**（AVAGO MegaRAID Configuration Utility **03.25.05.10**, LSI SAS3008, PCIe Slot 4）
  - **MegaRAID Advanced Software Options が全て [Enabled]**: `MegaRAID RAID6 [Enabled]` / `MegaRAID RAID5 [Enabled]` / `MegaRAID FastPath [Enabled]`。**これが RAID5/6/10 を作成できる根本理由**（プレミアム機能キーが有効化済み）。
  - **BBU [No]（バッテリバックアップなし）**。Create VD の既定 Write Policy は `[Write Back]` だが、無 BBU では電源断時のキャッシュ損失リスクがあり、実運用では Write Through 降格または BBU/CacheVault 装着を検討すべき。
  - 作成時の既定 VD パラメータ（既定のまま作成）: Strip Size [256 KB] / Read Policy [Read Ahead] / Write Policy [Write Back] / I/O Policy [Direct] / Access Policy [Read/Write] / Drive Cache [Unchanged] / Disable Background Initialization [No] / Default Initialization [No] / Emulation Type [Default]。
- ドライブ: SAS HDD **837.843GB × 4**（Unconfigured Good, **512B セクタ**, Drive Port 0 - 3:01:00〜03。10-13号機の 520B とは異なる）
- 接続: Redfish HTTPS + `--ciphers DEFAULT@SECLEVEL=0`、HTML5 KVM（cookie ログイン）
- 拠点間リンク: 高 latency（ping 59〜338ms, 0% loss）
- config: `config/training_tx1320.yml` / skill: `irmc-bios-raid`

## Web 調査結果（事前）

- PRAID EP400i = LSI SAS3108/SAS3008 系で RAID 0/1/5/6/**10**/50/60 をサポート（Broadcom/Fujitsu 公式データシート）。
- MegaRAID では RAID10 は **spanned RAID1**（2 台ずつのミラーを複数 span でストライプ）。UEFI HII の Create Virtual Drive で RAID Level に RAID10 を選ぶと span 構成 UI（"Add More Spans"）が現れる。
- 参照: Broadcom 12Gb/s MegaRAID Tri-Mode Software User Guide（"RAID 10 Drive Groups" / "Manually Creating a Virtual Drive"）、Fujitsu Modular RAID Controllers User Guide。

## dead-end 判定が偽陰性だった理由（実機で確認）

| 旧判定 (2026-05-17, FW 9.08F) | 今回の実機事実 (2026-06-02, FW 9.69F) |
|------|------|
| Create VD フォームは Save Config top から開き、ArrowDown が y=128 (Select RAID Level) を skip → 到達不可 | **フォームを開いた瞬間カーソルが `Select RAID Level [RAID0]` 行に乗っている**（右ヘルプも RAID Level 説明）。到達は自明 |
| Select RAID Level に到達できず RAID10 を選べない | `Select RAID Level` の Enter で開くドロップダウンに **`RAID0 / RAID1 / RAID5 / RAID6 / RAID00 / RAID10`** が並ぶ（0 ドライブ時点でも RAID10 在り） |
| Profile-Based VD も RAID0/1/5/6 のみで RAID10 profile 不在 | Profile 経路に依らず、通常の Create Virtual Drive で RAID10 を直接選択可能 |
| （カーソル検出が `[RAID0]` 明色 cluster で誤検出と自認） | per-key + 右ヘルプ全文/反転背景の文字読みで確実に同定（旧 pixel 検出の誤りを回避） |

旧判定は **古い FW + 旧ツール + カーソル検出不良の複合アーティファクト**であり、「行スキップ」は実態を反映していなかった。

## 実施手順（実機・per-key + サブエージェント画像分析）

1. **環境準備**: host Off 状態から `boot-override BiosSetup UEFI` + power on → BIOS Setup Main 到達（OEM screenshot 確認）。`scripts/irmc-kvm/server.py` を単一永続セッションで起動し master control 取得。Advanced タブ → `AVAGO MegaRAID <PRAID EP400i> Configuration Utility` → Enter → ダッシュボード（Status Optimal / Drives 4 / VD 1）。
2. **既存 VD クリア**: Main Menu → Configuration Management → Clear Configuration → 確認ダイアログ commit → 成功。Config Mgmt を一段 Escape → 再進入でメニューがリフレッシュされ `Create Virtual Drive` が出現（クリア成功の傍証）。
3. **RAID10 選択**: Create Virtual Drive → フォームはカーソルが `Select RAID Level [RAID0]` に乗って開く → Enter → ドロップダウン（RAID0/1/5/6/00/**10**）→ ArrowDown×5 で **RAID10** → Enter。フォームが `SELECT SPAN(S): / Span 0: / Select Drives / Add More Spans` に変化。
4. **Span 0**: `Select Drives` → drive popup → Drive :00 と :01 を Enabled（各ドライブ: Enter で Disabled/Enabled ドロップダウン → `mouse 230 384` でフォーカス → ArrowDown → Enter）→ Apply Changes → OK。
5. **Span 1**: `Add More Spans` → Span 1 生成 → Span 1 の `Select Drives` → drive popup（残り :02/:03 のみ表示）→ `Check All` → Apply Changes → OK。
6. **commit**: フォームに Span 0 + Span 1 + `Virtual Drive Size 1.636 TB` 表示。`Save Configuration` → 作成確認ダイアログ → commit レシピ → 1st ►OK（Enter）→ 2nd msg（Escape）。
7. **裏取り**: Main Menu → Virtual Drive Management → `Virtual Drive 0: RAID10, 1.636TB, Optimal`。VD0 プロパティで `Raid Level [RAID10] / Status [Optimal] / Size 1.636 TB`。KVM + OEM 真VGA の双方で確認。
8. host を ForceOff（RAID 構成はコントローラ NVRAM に永続）。**作成直後に Background Initialization が自動開始**（1%→3% と進行を観測）。host を電源断しても破損せず、次回起動時にコントローラ側で再開する想定で、VD は作成時点から Optimal で利用可能（init 完了を待つ必要はない）。

最終ドライブ割当: Span 0 = (3:01:00, 3:01:01) / Span 1 = (3:01:03, 3:01:02)。容量 1.636 TB = 全 raw 3.272 TB の半分（ミラー+ストライプ = RAID10）。これは storcli 経路の "RAID10 Optl 1.635 TB" と一致。

## 今回確立した重大ハードニング知見

1. **🚨 `keyrepeat` は高 latency 拠点で多重登録する** — 800ms 間隔で 4 press が約 6 行移動（1.5x）。**間隔 ≥1600ms で 1:1 になる**。精密ナビは `keyrepeat <key> <n> 1600` か単発 `press`（コマンドファイル 1 つ 1 キー）。
2. **🚨 確認ダイアログ/ドロップダウン操作は 1 コマンドファイルに集約** — 「ダイアログを開く Enter」と「`mouse→ArrowDown→Enter`」を別ファイルに分けると、間にフォーカスが失われ矢印が drop し ►No に当たって dialog がキャンセルされる（058/059 で実証 → 060 で 1 ファイル化して成功）。
3. **🚨 フォーカス確立クリックは「項目の上」を狙う。中央 (512,384) は不可** — 確認ダイアログ (Confirm/Yes/No) は開いた直後に `mouse 80 240`（左の項目帯）。中央 (512,384) はダイアログ項目が左上にあるため空白部に当たりフォーカスが付かない。
   - **Confirm の Disabled/Enabled ドロップダウンには別途クリック不要** — ダイアログ冒頭の `mouse 80 240` で得たフォーカスがドロップダウンにそのまま引き継がれ、ArrowDown→Enter で直接操作できる（Clear/Save の commit レシピを 1 コマンドファイルにまとめる前提）。
   - **ドライブの Disabled/Enabled ドロップダウンは `mouse 230 384`（ポップアップ箱の上）が必須** — これはドライブ行へナビゲートした後に別コマンドで開くためフォーカスが切れており、再クリックしないと ArrowDown が drop する（cmd 035 で実証、037 で 230 384 後に成功）。
4. **No → ArrowDown で Confirm に wrap**（`ArrowUp×2` より 1 キーで確実）。
5. **ドライブの Disabled/Enabled は dropdown を開いて `mouse 230 384` フォーカス必須** — フォーカス無しの ArrowDown も NumpadAdd 直接トグルも drop する。
6. **重い画面遷移（メニュー→フォーム）は 2.5s sleep でも stale スクショ**になり得る → 同じ前画面なら追加 sleep + 再 shot。
7. 作成 2nd msg は **Escape**、削除/作成 1st ►OK は **Enter**（挙動差）。
8. AVAGO メニュー階層・dashboard カウントは stale。VD の真値は **Virtual Drive Management** + OEM 真VGA で読む。

## 今後

### scripts/irmc-kvm/ への関数化の方針（推奨：プリミティブのみ昇格、全自動フローは保留）

全体を一発実行する `create_raid10()` 関数化は**時期尚早**と判断する。理由:

1. **手順が決定論的でない** — 成立したのは per-key + サブエージェント画像分析の**フィードバックループ**があったため。キー数カウントのナビは過剰登録（4 press→6 行）・オーバーシュートが頻発し、ダイアログのフォーカス喪失も間欠的だった。画面の文字を読まずに固定シーケンスを流す関数は、過去の dead-end や誤判定（`cycle_runner.py` が「caret 盲信欠陥」で昇格見送り）と同じ失敗をする。
2. **検証は 1 回のみ** — RAID0 の #73 ですら「3 サイクル反復再現」確認後に昇格した。RAID10 は成功 1 回かつ RAID0 より工程が多い（2 span・ドライブ個別 Enable・Add More Spans）。今コード化すると未検証の脆い手順を固定することになる。
3. **マジックナンバーが拠点依存** — `keyrepeat ≥1600ms`・mouse 座標 (80,240 / 230,384)・各 sleep は high-latency 拠点に最適化した値で、別機/別 latency で崩れる。
4. **ROI が低い** — training-tx1320 は一時設置の単機。RAID10 成立は実証・文書化済みで、繰り返し自動構築する常用ニーズは薄い。

**代わりに勧める中間案（低リスク・全 RAID 操作で再利用価値が高い）** — 今回の真の修正点である小さく堅牢なプリミティブを `scripts/irmc-kvm/kvmlib.py` に切り出す:

- `commit_confirm_dialog(...)` — 開く→項目上 mouse→ArrowDown(No→Confirm wrap)→Enter→Enabled→Yes を**1 連続シーケンス**で（フォーカス喪失対策込み）。
- `toggle_drive_enabled(...)` — Enter→`mouse 230 384`→ArrowDown→Enter。
- `nav_rows(n)` のデフォルト間隔を **≥1600ms** に（または単発 press ラッパー）。

そして **RAID10 の全体フローはスキル手順（per-key + サブエージェント検証）として SKILL.md に残す**（反映済み）。プリミティブのみ昇格し、判断は引き続き画面読みに委ねるのが、これまでの教訓に最も整合する。

- **今やるなら**: 上記プリミティブ 3 点の切り出し（コミットはユーザ承認後）。
- **全自動 `create_raid10()` 化は**: あと 2〜3 回の実機反復で再現性を確認してから。
