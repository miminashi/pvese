## 試行で判明した知見と恒久対策 (skill/doc/コード反映済み)

1. **進捗判定は sol-monitor.py の d-i stage で行う** — playground nginx access.log は空のことがあり
   (試行1) 進捗確認に使えない。完遂判定は sol-monitor rc=0 (POWER_DOWN→PowerState Off)。
2. 🐛 **known_hosts 鍵不一致** (試行2) — dark-net IP 使い回しで旧ホスト鍵が残り `StrictHostKeyChecking=no`
   でも MISMATCH 拒否される → `tx1320-pve-setup.sh` に **`-o UserKnownHostsFile=/dev/null`** を追加。
3. 🚨 **sonnet の途中 yield** (試行3、最重要) — sol-monitor を `run_in_background` 化して「通知を待つ」と
   ターンを終え、install 監視中に停止 → **runbook + プロンプトに「sol-monitor は foreground・最終報告まで
   yield 禁止、harness が background 化しても Read ポーリングで待ち切る」を明記**。試行4 以降で再発せず。
4. **`wait_ssh` の無駄待ち** (試行5) — 最終 reboot の IP 変動時に死んだ旧 IP へ 420s 待ってから再 discovery
   → **既知 IP と MAC 再 discovery を毎サイクル交互に試すインターリーブ方式**に書き換え。
5. **#15 (d-i netcfg stuck, ~30-50%)** — deploy から合計 ~10min 停滞で ForceOff → Step 2 から再 deploy
   (2回目で即解消)。試行1/2/6/8/9 で発生し、すべて runbook 手順どおり吸収。
6. **RAID10 直読** — storcli は OS 標準に無いため `tx1320-pve-setup.sh` の検証ステップで storcli64.bin を
   playground から自動 wget して `/c0/vall show` を直読 (e2e 補足A の「直読していない」弱点を解消)。
7. **PVE install ログの巨大化** (試行8) — 初回 install で apt deferred trigger 警告 `W: Tried to start
   delayed item` が ~220万行 (119MB) 出力 (無害) → runbook に「全 Read 禁止・grep/tail で要点確認」注記。
8. 🐛 **ConnectCD HTTP500 サイレント失敗** (試行9) — ForceOff 直後の即再 deploy で iRMC CD worker 不整合で
   ConnectCD が 500 を返し `|| true` で握り潰され、**CD 未接続のまま boot-override Cd が設定→旧 HDD GRUB
   起動**のサイレント失敗 → `irmc-ipxe-cd-deploy.sh` の ConnectCD を「204 まで VirtualMediaServiceRestart +
   リトライ、ダメなら deploy abort」に強化。
9. **opus 側 BIOS Clear のタブ着地** — `server.py` READY 後は実際は常に Main タブだが `server_ready.png` の
   size 指紋は当てにならない (Advanced 指紋が出ても cursor は Main、試行4)。**READY 後は size で分岐せず常に
   単一 ArrowRight → shot で Advanced 確認**。タブは wrap する (Main で ArrowLeft は Save&Exit へ、試行5) ので
   ArrowLeft 強制は不可。ArrowRight ドロップ (試行7/8) は shot 検証 + 再送で吸収。

## 再現方法

opus (オーケストレータ) 側、各試行:
```sh
# 1. BIOS HII KVM RAID Clear (opus)
./oplog.sh ./scripts/irmc-kvm-recover.sh config/training_tx1320.yml tmp/<sid>/recover.jpg 175
.venv/bin/python scripts/irmc-kvm/server.py --bmc-ip 10.254.254.9 --bmc-user claude \
    --bmc-pass Claude123 --srv-dir tmp/<sid>/srv-tN --idle-timeout 3600 &   # READY 待ち
# in/NNN.cmd を順に投入 (size 指紋で検証): ArrowRight→tab(17919) / navy 393→avago(18051) /
#   Enter×3+ArrowDown→clearrow(10135) / modal commit→vdm(9758=VDなし) / quit
#   ※ tab が 14600 (Main 居残り=ArrowRight ドロップ) なら ArrowRight 再送

# 2. sonnet エージェントを spawn (Agent: general-purpose, model=sonnet)
#    プロンプト = pxe-deploy SKILL.md の runbook 節を上から実行 + 試行番号 + 既知の注意点 + 報告テンプレ
#    (anti-yield: sol-monitor は foreground・最終報告まで yield 禁止 を強調)

# 3. 報告受領 → runbook/スクリプト改善 → 反復ログ追記 → 次試行へ
```

sonnet 側 (runbook 通り、ステップ2〜6):
```sh
mkdir -p tmp/<sid>/trialN
export BMC_SCHEME=https BMC_CURL_OPTS="--ciphers DEFAULT@SECLEVEL=0" POWER_ON_RESET_TYPE=On \
    BMC_PATCH_REQUIRES_ETAG=1 BMC_BOOT_OVERRIDE_NO_DISABLED=1
./oplog.sh ./scripts/irmc-ipxe-cd-deploy.sh config/training_tx1320.yml ipxe-tx1320.iso
.venv/bin/python scripts/sol-monitor.py --bmc-ip 10.254.254.9 --bmc-user claude --bmc-pass Claude123 \
    --log-file tmp/<sid>/trialN/install.log --timeout 2400 --powerstate-interval 30   # foreground
#   DETECTING_NETWORK で合計~10min 停滞なら #15 → forceoff → 再 deploy
./oplog.sh ./scripts/bmc-power.sh boot-override 10.254.254.9 claude Claude123 Hdd UEFI
./oplog.sh ./scripts/bmc-power.sh on 10.254.254.9 claude Claude123
# eno2 IP 特定: /24 ping-sweep → ip neigh | grep 4c:52:62:14:de:f0
./oplog.sh ./scripts/tx1320-pve-setup.sh config/training_tx1320.yml <ip>
# 検証: pveversion / systemctl is-active / curl https://<ip>:8006 / storcli /c0/vall show
```

## 補足

- **全試行の最終 IP が .16 に収束**: eno2 DHCP は reboot ごとに変動するが (pre-reboot で .5/.8/.20/.22/.23 等)、
  最終 PVE reboot 後は毎回 .16 に落ち着いた。`wait_ssh` の MAC 再 discovery がこれを吸収。
- **所要時間**: 1 試行あたり install ~10-25min (cross-site link 速度依存) + PVE setup ~30-55min。
  BIOS Clear (opus) は ~7-8min (recover ~5min + KVM clear ~3min)。
- **BIOS Clear が唯一の opus 手作業**: 検証付き手順 (size 指紋 + 要所サブエージェント判読) で 10/10 成功。
  ArrowRight ドロップ (試行7/8) は shot 検証 + 再送で吸収、低 latency 環境では概ね一発成功。BIOS Clear の
  サブエージェント判読は試行1 で size 指紋 (tab=17919/avago=18051/clearrow=10135/vdm=9758) を確定後、
  試行2以降は size 一致を基本にし anomaly 時のみ判読する効率化を採った (10/10 で誤判定なし)。
- **sol-monitor の rc=4 は #15 の ForceOff 時の想定挙動** (試行9): #15 エスケープで監視中に ForceOff すると
  sol-monitor は POWER_DOWN でなく途中打ち切りで **rc=4 (false positive) を返す**。これは異常ではなく
  ForceOff した結果で、完遂判定は再 deploy 後の sol-monitor rc=0 で行う (runbook Step 3 に明文化)。
- **install/PVE setup 中の無害エラーメッセージ** (本作業で観測、いずれも処理継続・無害):
  `Error: ipv4: Address already assigned` (PVE 構成中の ifupdown2 が eno1 に再アサイン、試行8) /
  deploy の `disconnect-cd` HTTP400 (FW 9.69F の OEM action 名変更) / PowerOn `ActionParameterValueNotInList`
  (PowerState=On 時の ResetType=On 拒否) — 後 2 つは deploy スクリプトの `|| true` ガード済み。
- **RAID10 を毎試行 OS 上で直読**: 本 10 試行は `storcli64 /c0/vall show` で `RAID10 Optl 1.635TB` を
  毎回 OS 上から直読した (3試行 e2e レポート補足A の「Optimal を直読していない」弱点を解消)。

## 結論

通常セットアップ (iPXE-CD deploy → install → disk boot → IP特定 → PVE通し) は、新設した **runbook 節を
sonnet が参照するだけで自律完遂できる**ことを 10 試行で確定 (9/10 完全自律、対策後 7 連続自律成功)。
試行ごとに判明した落とし穴・バグ (sonnet 経路の 8 件 = nginx/known_hosts/yield/wait_ssh/#15/RAID直読/
巨大ログ/ConnectCD、上記「知見」項目1〜8) はすべて skill/runbook/スクリプトに恒久反映済みで、収束
(直近の試行は無修正完走) を確認した。RAID 初期化 (BIOS HII KVM Clear) は通常セットアップ外の前処理として
opus が担い、検証付き手順 (知見項目9 のタブ着地ハードニング込み) で 10/10 成功した。
