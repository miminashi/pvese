## 前提・目的

[Phase 4 レポート](2026-05-07_053810_server10_hw_err_phase4.md) で:
- Plan B-alt (sda 上 Debian + AOS ISO の GRUB loopback boot) は Toshiba SSD MBR を dd で誤って消去 → boot loop に陥り未完成
- BMC VirtualMedia 経由の AOS imaging は `tar.p00` 読み込みが ~10 分以上停滞 (BMC ~10Mbps 帯域制約) で打ち切り
- Phase 3-4 の結論: 「Nutanix-OEM Seagate opcode filter は drive firmware に焼かれており host OS から bypass 不能」だが、Phoenix CE installer 自体が opcode filter を bypass する内部 API を持つかどうかは未検証

本 Phase 5 では:
1. boot loop を復旧
2. AOS Phoenix Foundation imaging を実際に走らせて Phoenix が Seagate にどう触れるか観察
3. Phoenix が opcode filter を bypass しないことを最終確認 (または bypass 経路を発見)

完了条件: pve10 の Seagate (sdb/sdc) で `dd if=/dev/zero of=/dev/sdX bs=512 count=1 oflag=direct` が **Phoenix からは成功する** か、または **依然として失敗** することを観察。

## 🎯 Phase 5 の最終結論

### 1. Nutanix-OEM Seagate opcode filter は **Phoenix CE installer の SVM imaging すらブロック**

Phoenix SVM imaging はインストール初期で `pre_svm_rescue` を呼び対象 disk への `os.fsync` を行うが、Seagate 上ではここで EIO で死ぬ。Phoenix 自身が標準カーネル I/O (`os.fsync`) を使うため、特殊な bypass 経路は存在しないことが判明。

### 2. Phoenix shell から直接 dd しても Remote I/O error

`dd if=/dev/zero of=/dev/sd[bc] bs=512 count=1 oflag=direct` は Phoenix 内でも 0 bytes copied。一方 Toshiba SSD (sda) への seek=10000 dd は 512 bytes copied で成功するため、これは「Seagate 個体」かつ「特定 LBA に依存しない一律の opcode reject」を意味する。

### 3. drive firmware の opcode filter は drive 内部論理に焼かれており host OS の種類 (Linux / Phoenix CE / etc.) に関係なく block される

Phase 3-4 の仮説 (firmware filter) を Phoenix で実証。Phoenix が Nutanix 純正 image にも関わらず write を通せないので、「Nutanix internal API で bypass」も否定された (少なくとも Phoenix Foundation 5.6.1 + AOS 6.8.1 GA の installer がそれを使えていない)。

### 4. Phase 4 で「BMC 帯域問題」とされた tar.p00 停滞は単なる時間の問題

実際には ~50 分待てば完走する。Phase 4 では 10 分時点で打ち切ったが、Phase 5 で完走を確認。「BMC ~10Mbps が制約」は事実だが「不可能」ではない。Phase 4 の「Plan B-alt 切替」判断の根拠は時間効率のみで、BMC 経由 imaging の実現性自体は Phase 5 で立証された。

### 1. boot loop の発生条件 (Plan B-alt の罠を再現したい場合)


### 2. C1 GRUB loopback boot の PHOENIX label 失敗を再現

```sh
# Debian で /etc/grub.d/40_phoenix_loopback を配置 (LVM root UUID 指定):
cat > /etc/grub.d/40_phoenix_loopback <<'EOF'
#!/bin/sh
exec tail -n +3 $0
menuentry 'Phoenix CE (loopback v2)' {
    insmod part_msdos
    insmod ext2
    insmod lvm
    set root_uuid=46fe3fe3-ce8d-41be-96a9-70eeea35a648
    search --no-floppy --fs-uuid --set=root $root_uuid
    set isofile=/aos-ce.iso
    loopback loop $isofile
    linux (loop)/boot/kernel init=/ce_installer intel_iommu=on iommu=pt kvm-intel.nested=1 kvm.ignore_msrs=1 kvm-intel.ept=1 vga=791 net.ifnames=0 IMG=squashfs findiso=$isofile iso-scan/filename=$isofile rd.live.image rd.live.dir=/
    initrd (loop)/boot/initrd
}
EOF
chmod +x /etc/grub.d/40_phoenix_loopback
update-grub
grub-reboot 'Phoenix CE (loopback v2)'
reboot
# Phoenix kernel boot 後 [15/15] で Phoenix ISO not found → livecd files not found エラー
```

## 残された可能性 (claude 実施可能だが期待値ほぼゼロ)

### A. Seagate firmware reverse engineering / 物理 serial 取得経由の FW 上書き

Phase 3-4-5 を通じ Phoenix CE installer の Nutanix 公式 SVM imaging すら opcode filter を bypass できないことが判明した以上、host 側で打てる手段は drive firmware の上書き以外残っていない。これは `apps1.seagate.com` でアカウント登録 + 物理 serial 入手が前提で、Phase 4 で確認したとおりリモート不可能。

### B. drive を Nutanix 純正サポート経由で再認証する (要 Nutanix サポート契約)

claude 実施不可。Nutanix サポートに drive の opcode filter 解除リクエストを出す必要があり、本ラボ環境では選択肢に無い。

### C. Phase 4 で Track A (Seagate FW) を諦めた件は Phase 5 でも変わらず

物理 serial 取得経路がリモート存在しないため確定不可。

## ギブアップ判断基準 (Phase 4 と同一だが別観点で確定)

Phase 4 では「BMC 帯域で時間切れ」のため打ち切ったが、Phase 5 で実際に完走させた結果:
- BMC 帯域問題は不便だが解決可能 (~50 分待てば良い)
- しかし完走しても Phoenix 自身が Seagate に書けないため imaging は最終的に失敗
- → ハードウェア側の制約 (drive firmware の opcode filter) が真の壁であり、host OS / installer の選択では超えられない

これにより Issue #61 の「LINSTOR 4 ノード構築 + ベンチマーク」は **データ HDD (Seagate) を LINSTOR storage backend として組み込めない** 限定で blocked。代替: Toshiba SSD のみで構築するなら可能だが LINSTOR の意義 (HDD でのスループット計測) と相反する。
