## 前提・目的

前セッション (virtual-wolf) で N1 仮説 (setpathinfo の chmod EPERM 起因) を反証。 setpathinfo / smb_posix_open / smbXsrv_open_create はすべて NT_STATUS_OK で成功するが、 iRMC は USB device を生成せず ~320ms 後に close → 60s 沈黙 → retry を継続する状態。 force user=nobody は AIO read 抑制の副作用を持つと推定された。

本セッションは **N2 仮説 = 「特定 ISO 内容が iRMC 想定と違って abort」** を検証するため、 純正 Debian ISO (`debian-13.3.0-amd64-netinst.iso`) を VirtualMedia source に切り替え同じ trigger sequence を実行。 attach 成立すれば N2 確定、 不成立なら N2 反証で N3/N4 へ持ち越し。 smb.conf は `[global] log level = 10` 1 行追加のみで [public] には触らない (force user 設定は無し)。

## 重要な発見 (next-session must-read)

### 🎯 1. **N2 反証確定**: 別 ISO でも attach 不成立、 挙動は元 ISO と完全同一

Phase 2 で `debian-13.3.0-amd64-netinst.iso` (純正 Debian 13.3 amd64 netinst、 790 MB、 owner=ubuntu:ubuntu、 0664) に切り替えて ConnectCD trigger、 120s polling の結果:

| 観測 | 値 |
|------|-----|
| Members.count 24 iter (120s) すべて | **0** |
| AllowableValues に `DisconnectCD` 出現 | **なし** |
| iRMC give-up state | **解除済** (Phase 1 Manager.Reset 後、 Samba session 確立) |
| Samba 側の effective uid | 65534 (nobody) ★ map to guest = bad user の効果、 force user 未設定でも同じ ★ |
| setpathinfo `info_level=521` | NT_STATUS_OK |
| smb_posix_open mode 0755 | NT_STATUS_OK |
| smbXsrv_open_create | NT_STATUS_OK |
| 60秒 retry サイクル | **継続** (17:14:57 / 17:15:58 / 17:16:59 / 17:18:00 で 4 cycle 観測、 23 分間で計 8 cycle) |
| ~320ms 後 close パターン | **完全に同じ** |

つまり ISO の内容 (filesystem header、 Boot Catalog、 El Torito、 file size) は真因ではない。 N2 反証。

### 🎯 2. **🎯🎯 新真因候補 N6 発見: iRMC は qfsinfo level=513 (0x201) を要求するが Samba は NT_STATUS_INVALID_LEVEL を返す 🎯🎯**

Samba debug log で全 cycle に共通する **NT error packet** を発見。 これが本セッション最大の収穫:

```
[2026/05/20 17:14:39.863288] call_trans2qfsinfo: level = 513
[2026/05/20 17:14:39.863310] smbd_do_qfsinfo: level = 513
[2026/05/20 17:14:39.863336] NT error packet at source3/smbd/smb1_trans2.c(1686) cmd=50 (SMBtrans2) NT_STATUS_INVALID_LEVEL
```

これは 60s retry の **毎 cycle で必ず発生** (17:14:39 / 17:16:38 で再現確認)。 Samba ソース `source3/smbd/smb1_trans2.c:1686` は `call_trans2qfsinfo` の info_level switch の default 句 → 未知 level でフォールスルー → `NT_STATUS_INVALID_LEVEL` を返す。

iRMC が送る trans2 シーケンス (本セッションで完全確定):

```
1. call_trans2qfsinfo  level=513 (0x201)  ← NT_STATUS_INVALID_LEVEL  ★ Samba 未対応 ★
2. call_trans2qfsinfo  level=259 (SMB_QUERY_FS_SIZE_INFO)  → NT_STATUS_OK
3. call_trans2qpathinfo level=512 (SMB_QUERY_FILE_UNIX_BASIC)  → NT_STATUS_OK
4. call_trans2setpathinfo info_level=521 (SMB_SET_FILE_UNIX_BASIC, chmod 0755 試行)  → NT_STATUS_OK
5. smb_posix_open mode=0755 flags=1024 → NT_STATUS_OK (open_global_id 取得)
6. ~320ms 後 reply_close (USB device 生成失敗)
7. 60s 沈黙
8. → step 1 へ戻り retry
```

**level 513 (0x201) は Samba ソース** (4.19-Ubuntu) **で未定義**。 SMB CIFS UNIX 拡張仕様で:
- 0x200 (512) = SMB_QUERY_CIFS_UNIX_INFO
- 0x201 (513) = **未定義** ← iRMC が要求している level
- 0x202 (514) = SMB_QUERY_POSIX_FS_INFO

考えられる解釈:
- iRMC FW 9.08F の SMB UNIX 拡張 client は Microsoft の SMB UNIX 拡張仕様 (古い draft) または Fujitsu OEM 独自 level として level 513 を要求し、 response 内容を「remote share の UNIX 拡張 capability flag」として解釈する
- Samba が INVALID_LEVEL を返すと、 iRMC は **拡張未サポート mode** にフォールバックして file open まで進むが、 **USB device 生成段階でこの flag が必須** で abort する
- もしくは iRMC は INVALID_LEVEL を「retry が必要」と解釈して 60s 後に同じ sequence を繰り返す

これが **N6 仮説** = 真因候補。 次セッションで level=513 の意味を Samba ソース + Microsoft SMB UNIX 拡張仕様で確定し、 Samba を patch して NT_STATUS_OK + ダミー response を返すよう試行することで検証可能。

### 🎯 3. **前セッションの「force user=nobody は AIO read 抑制副作用」推論を訂正**

本セッション (smb.conf 無改変、 force user 未設定) でも AIO read は **0 件**。 つまり AIO read 不在は force user 設定の有無に依存しない。 anonymous SMB session (map to guest = bad user) の場合、 effective uid は元から 65534 (nobody) になるため、 force user=nobody を追加で設定しても uid は同じ → 挙動も同じ。 前セッションの「副作用」推論は誤解。

→ 真の答え: iRMC は **smb_posix_open response 後に read を発行せず close する** のが本来の挙動。 これは「open で得た情報だけで USB device を生成するかどうか決定する」という iRMC の設計、 もしくは「open 後に level=513 などの後続 query で fail したから abort」のどちらか。 N6 仮説と整合する。

### 🎯 4. **60s retry cycle は依然継続**

iRMC は failure を 60s 待って同じシーケンスで retry。 本セッション 23 分の log 期間で 8 cycle (毎 ~60s 間隔) を観測。 cycle 開始時の各 trans2 timing は 1 cycle ~320ms (setpathinfo → posix_open → close) で完了して残り ~59.7s は沈黙。

### 🎯 5. iRMC give-up state は数時間で自然解除 (本セッションでも再現)

前セッション末 (5/20 14:43) から本セッション開始 (15:00) まで 17 分。 Phase 1 で Manager.Reset 実施 (HTTP 204) → 復帰まで **約 256 秒** (前セッション 105s より長め、 ServiceTemporarilyUnavailable 期間も長め)。 これは GracefulRestart の標準化されていない動作 ≈ 標準範囲内。 give-up state は前セッションと同じく自然解除可能。

### 6. パケットレベルの観察 (前々セッション pcap との整合)

前々セッションの pcap で観測された「AIO read まで到達」記述は、 本セッション + N1 セッション双方で再現できなかった。 おそらく前々セッションでは:
- (a) log level が低かったため AIO read 関連ログのみ packet 解析と推測でつないだ可能性
- (b) 当時の smb.conf が異なる設定 (例: `vfs objects = ...` で AIO 有効化) になっていた可能性
- (c) 単純に解釈ミス (TCP segment 内の SMB header を誤読)

いずれにせよ本セッションでの観測「AIO read 一切なし」が正しく、 真因は level=513 にあると見るのが妥当。

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🎯 真因候補は qfsinfo level=513**: 前セッションまでは「smb_posix_open 後の何か」と漠然と推定していたが、 本セッションで `log level=10` の Samba debug log を **NT_STATUS で grep して non-OK を全件確認** することで `INVALID_LEVEL` を発見。 真因候補が **smb_posix_open より前** (qfsinfo phase) にあると確定したのは大きな前進。 **次セッションは N6 検証を最優先**
2. **教訓 N1 セッションの「force user=nobody 副作用」推論は誤り**: anonymous SMB session (map to guest = bad user) では Samba は元から effective uid=65534 (nobody) で動作する。 force user=nobody を追加で設定しても uid は同じ、 つまり「force user の有無で挙動が変わる」観測は本来あり得ない。 N1 セッションでは log level=2 程度で AIO read 関連ログが見えなかっただけと推察。 **仮説間で挙動差を観測したら、 まず log level=10 で grep し直すこと**
3. **NT_STATUS の grep は積極的に**: Samba debug log を `grep -E 'NT_STATUS' | grep -v NT_STATUS_OK | grep -v NT_STATUS_WAS_UNLOCKED` でフィルタすると、 通常見落とす INVALID_LEVEL / INVALID_PARAMETER 系のエラーを発見できる。 これは前セッションでも本来やるべきだった
4. **iRMC が送る trans2 シーケンスは本セッションで完全像確定** (Section 2 参照)。 これは N3/N5 検証時の baseline として有用
5. **iRMC give-up state の Manager.Reset 復帰時間は variable** (105s / 256s)。 30s pre-sleep + 5s 間隔 polling で 40 iter (約 200s) は安全圏、 さらに延長する余地もあり。 GracefulRestart の HTTP 204 はあくまで「Reset 開始受付」を意味する
6. **smb.conf 変更時の互換性保護は確立**: backup → 適用 → 復元 → diff 0 + smbclient -L baseline 比較で完全保護。 sudo 操作は `! sudo sh tmp/<sid>/phaseN.sh` で依頼するパターンが運用負荷少なく確実
7. **ping baseline 231ms / 0% loss は前 3 セッションと同水準**。 ネットワーク経路は安定。 次セッションでも precheck で大幅悪化なければ即 N6 検証に進んで OK
8. **次セッション最優先**: Samba ソース `source3/smbd/smb1_trans2.c` で `case 513` または `0x201` を grep。 不在を確認した上で、 Microsoft SMB UNIX 拡張 spec (おそらく SambaXP papers / [MS-CIFS] / Linux kernel cifs.ko の info_level 一覧) で level 513 の意味を特定する
