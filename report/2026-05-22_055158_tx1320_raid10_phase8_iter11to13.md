## 結果サマリ

### iter11 (default cmdline)

| 計測 | 値 |
|------|---|
| SOL 行数 | 275 行 |
| GRUB cycle 数 | **33 回** (5 分間) |
| サイクル時間 | 約 9 秒/cycle |
| kernel printk on SOL | **0** 行 |
| 実 VGA (user 報告) | `[ 0.75872] x86/cpu: SGX disabled or unsupported by BIOS.` **stable で 5 分継続** |
| OEM Screenshot | BIOS POST 92 / 99 / `Booting Automated Install` 等を正常 capture |

**判定**: triple-fault reset loop。 Phase 3-5 の「silent hang」は実は triple-fault loop の累積観測だった。 kernel は 0.76 秒まで正常に動き SGX detection 完了 → 直後に triple-fault → 暖機 reset (BIOS POST スキップ) → GRUB → 同じ kernel → 同じ triple-fault。 9 秒サイクルで毎回 VGA に SGX 行を再描画するため user 視点では「stable」に見える。

### iter12 (`earlyprintk=efi,keep loglevel=8 debug initcall_debug ignore_loglevel`)

| 計測 | 値 |
|------|---|
| SOL 行数 | 141 行 |
| GRUB cycle 数 | **13 回** (6 分間) |
| サイクル時間 | **約 28 秒/cycle** (iter11 の 3 倍) |
| kernel printk on SOL | 0 行 |
| 実 VGA (user 報告) | `Booting `Automated Install`` のみ (SGX 行さえ見えない) |

**判定**: debug flags + earlyprintk=efi,keep でサイクル時間が 9s → 28s に伸びる = kernel が約 19 秒長く走っている。 ただし printk は UEFI ConOut にルートされ iRMC が ConOut を VGA に bridge していないため VGA に出ない。 kernel は最終的にやはり triple-fault する。

### iter13 (`earlyprintk=ttyS0,115200,keep` のみ追加)

| 計測 | 値 |
|------|---|
| SOL 行数 | 66 行 (うち GRUB 0 行、 全 "Session operational" reconnect message) |
| GRUB cycle 数 | **0 回** (5 分間) — iter13 / iter13-retry 両方再現 |
| サイクル時間 | N/A (cycling していない) |
| kernel printk on SOL | 0 行 |
| OEM Screenshot @ t+180s | `Booting Automated Install` + cursor |
| OEM Screenshot @ t+340s | `Booting Automated Install` + cursor (**完全に同一**) |

**判定**: **kernel HANG (triple-fault loop ではない)**。 PowerState=On 継続、 VGA も 5 分 40 秒同一画面 = CPU reset が発生していない。 `earlyprintk=ttyS0,115200,keep` 追加で kernel は早期 ttyS0 init (BIOS PNP / ACPI 前の hardcoded I/O port 0x3F8 write) で hang した。 iter11 の triple-fault point は早期 ttyS0 init を **越えた後** の何か (mtrr / apic / SGX detection 周辺) で起きていた。

### 🎯🎯 Phase 8 で得た 4 つの確定知見

1. **Phase 3-5 silent hang = triple-fault reset loop**: iter11 default cmdline + 実 VGA 観測 + SOL 33 cycles で確定
2. 🎯 **iRMC OEM Screenshot (Redfish action) は KVM canvas artifact を完全に回避する真の VGA capture 経路**: Phase 7 で発見した KVM viewer の framebuffer artifact 問題への解決策。 BIOS POST text、 POST code、 `Booting` テキスト等を正常 capture できる
3. **iter12 debug flags でサイクル時間 9s → 28s**: kernel が約 19 秒長く走る (printk は UEFI ConOut に隠れる)
4. **iter13 earlyprintk=ttyS0 で挙動が triple-fault loop → kernel hang に変化**: D3373 で hang 経路に入るため今後使わない

## 教訓

- **iRMC OEM Screenshot (`scripts/irmc-oem-screenshot.sh`) を VGA capture の最優先手段にする**。 KVM canvas / locator screenshot は補助のみ。 framebuffer mode 変更後の artifact から完全に解放される (Phase 8 で実証)
- **VGA 観測 + SOL GRUB cycle 数 + PowerState polling の三点測定で kernel state を判別**: cycling = triple-fault loop / 静止 + On = hang / 静止 + Off = power down。 単一証拠だけでは判別不能
- **debug flags でサイクル時間が変わる**ことから kernel が boot 経路を辿る距離 (秒数) を間接的に測定可能。 9s → 28s は大きなシグナル
- **`earlyprintk=ttyS0,115200,keep` は D3373 では使わない** — kernel が hang し、 SOL も完全沈黙する。 観測手段を失う
- **user の実 VGA 観測は OEM Screenshot を上回る情報量**を持つ (persistence of vision で 0.5 秒モーメントを「stable」として認識できる)。 高価値なので 1 session 1 回ペースで使う
- 各 iter の ISO build + 配置 + attach + boot + 観測サイクルは 約 7-10 分。 5 cycles で 1 session 終了が現実的
