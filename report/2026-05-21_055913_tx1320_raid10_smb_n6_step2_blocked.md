## 前提・目的

前セッション [s-quizzical-wozniak](2026-05-20_231624_tx1320_raid10_smb_n6_step1.md) で Samba 4.19.5 の `source3/smbd/smb2_trans2.c:2026` の typo bug (`#if defined(SMB1SERVER)` ← 本来 `WITH_SMB1SERVER`) を真因として確定し、 1 文字 patch 案を作成済。 本セッションはその実証 (N6 step 2) として:

1. ユーザ提供の root 自由サーバ **10.1.6.6** を build host 兼 SMB server として使用
2. Samba 4.19.5 ソースに patch 適用 + 再 build
3. patched smbd を 10.1.6.6 上の `/usr/sbin/smbd` と差し替え
4. iRMC を 10.1.6.6 へ向け、 SMB attach 検証 → level=513 INVALID_LEVEL が消失することを確認
5. attach 成立後、 OS install まで実走

を目標とした。

## 重要な発見 (next-session must-read)

### 🎯 1. **patch + build は完全に成功している**

- Samba 4.19.5 source tarball (sha256=`0e2405b4cec29d0459621f4340a1a74af771ec7cffedff43250cad7f1f87605e`) を 10.1.6.6 へ scp

- `./configure --prefix=/usr --libdir=/usr/lib/x86_64-linux-gnu --sysconfdir=/etc --localstatedir=/var --with-piddir=/run/samba --with-pammodulesdir=/lib/x86_64-linux-gnu/security --enable-fhs` → 1m37s で成功

- `bin/default/source3/smbd/smbd --version` → "Version 4.19.5" を確認
- 出力 binary は ELF 64-bit pie, dynamic linked, x86-64, 98 KB

### 🎯🎯 2. **iRMC SMB worker は本セッション開始時点で完全に inactive (give-up state)**

これが本セッションの予想外の最大の発見:

- iRMC OEM VirtualMedia の `CDImage` を 10.1.6.6 に PATCH しても、 iRMC は 10.1.6.6 へ **TCP 1 packet も送らない**
- 同期 (foreground) tcpdump で 4-6 分監視しても 0 packet (`0 packets captured` / `1 packet received by filter`)
- iRMC InternalEventLog の最新エントリは 2026-05-17T13:09:49 EDT — **本セッションの操作 (Manager.Reset, PATCH, VirtualMediaServiceRestart 等) も含めて 4 日間ログが更新されていない**
- iRMC config を 10.1.6.1 (本来の動く SMB host) に戻しても、 同じく無反応 (`ss -tn` で 10.254.254.9 ↔ local 10.1.6.1 接続なし、 90s 監視)

これは iRMC FW 9.08F の **SMB worker サブシステム自体が完全停止** したことを示す。 前セッション報告の「給与 give-up 状態と思われ Manager.Reset で 256s 復帰」より重篤。

### 🎯 3. **完全リセットも復帰させない**

実施した復旧操作:
1. **`FTSManager.VirtualMediaServiceRestart`** (VirtualMediaType=CD、 HTTP 204 成功) → 効果なし
2. **`Manager.Reset` (ResetType=ForceRestart)** (HTTP 204 成功、 BMC が 165s 後に Redfish 復活) → 効果なし、 SMB worker 復活せず
3. **PATCH umount → 5s 待機 → PATCH config 再投入** (フレッシュトリガー) → 効果なし
4. **host power-cycle (forceoff + boot-override Cd UEFI + on)** (host POST + UEFI 読み込み → CD 要求 → SMB worker 起動を期待) → 効果なし

### 4. **ネットワーク疎通は完全に正常**

- 10.1.6.6 → 10.254.254.9 (iRMC): ping 0% loss / 100-470ms (latency は記録済み, [network_latency memory](https://example/training_tx1320_network_latency.md))
- 10.1.6.6 → 10.254.254.9 port 22 (SSH): nc 接続成功
- 10.1.6.6 → 10.254.254.9 port 443 (HTTPS Redfish): nc 接続成功
- ICMP echo packets 10.1.6.6 ↔ iRMC は同期 tcpdump で正常観測 (`ens19 In/Out IP 10.254.254.9 ...`)

したがって 10.1.6.6 が iRMC SMB target として使えない原因は **網ではなく iRMC FW 内部の SMB worker の停止**。

### 5. **patched smbd は ABI 適合確認済 (10.1.6.6 上で動作)**

- 10.1.6.6 上で `~/samba-build/samba-4.19.5/bin/default/source3/smbd/smbd --version` → Version 4.19.5
- RUNPATH は build dir 固定 (`/home/ubuntu/samba-build/samba-4.19.5/bin/shared:.../private`)
- 10.1.6.1 local で実行すると `libsecrets3-samba4.so` (unversioned) が見つからずエラー (system は `.so.0` versioned)
- 解決には (A) `LD_LIBRARY_PATH=/opt/samba-patched/shared` + tarball 展開、 (B) `chrpath -r /usr/lib/x86_64-linux-gnu/samba` で RUNPATH 書き換え + system に unversioned alias 作成、 のいずれかが必要 ([install-instructions.md](attachment/2026-05-21_055913_tx1320_raid10_smb_n6_step2_blocked/install-instructions.md) 参照)

### 6. **10.1.6.6 SMB setup は完全に正常稼働**

- samba 2:4.19.5+dfsg-4ubuntu9.4 install + smb.conf 作成 + smbd/nmbd 起動 → 成功
- `smbclient -L //10.1.6.6/ -U guest%guest -m NT1` → public share 一覧表示
- 10.1.6.6 内のローカル smbclient テストは全て成功 (samba 自体は完全に機能している)
- iRMC が SMB ハンドシェイクを開始すれば、 unpatched なら INVALID_LEVEL → patched なら成功 を観測できる状態を作れている

### 2. **🚨 iRMC SMB worker の復活手段が必要**

local 配布で patched smbd が動いても、 **iRMC が SMB を試みなければ意味がない**。 本セッションで Manager.Reset / VirtualMediaServiceRestart / PATCH / power-cycle すべてが効かなかった。 次セッションで検討すべき:

| 復旧手段 | リスク | 推奨度 |
|---------|--------|---------|
| **(a) iRMC の物理電源切離 (筐体電源を完全 OFF + AC コード抜き 30s + 再投入)** | host 業務影響 (host 自体は今回オフだが、 一時設置のため許容範囲) | **★★★ 推奨** |
| **(b) iRMC FW を 9.08F → 同 9.08F に再 reflash** (FW 更新でなく同 version の reapply) | reflash 中の BMC 障害リスク | ★★ |
| **(c) iRMC FW を別 version (より新しい / 古い) に更新** | 既知の動作と異なる可能性 / ライセンス制約 | ★ |
| (d) Manager.Reset を複数回連続実行 (4-5 回繰り返し) | 効果未知 | ★ |
| (e) iRMC 設定を save → factory default reset → restore (config 残しつつ全 worker 再 init) | factory default 中の通信断 | ★ |
| (f) `pveceph` 風の iRMC SMB diagnostics があれば実行 | iRMC FW 9.08F に存在しない可能性 | (要調査) |

最初は **(a) 物理電源切離** を試すのが ROI 最大。 user に依頼:
> "training-tx1320 (10.254.254.9) の筐体電源を完全に切断 (AC コード抜き) → 30 秒以上待機 → 再投入 → iRMC が boot 完了したら知らせてください"

## 重要な教訓 (次セッションへの引き継ぎ)

1. **🚨 patch が verified correct でも、 verification 経路は network / FW で詰まり得る**: 本セッションは patch 本体 (typo fix) の build + 動作 (`--version`) は完璧に成功しているが、 iRMC FW 9.08F の SMB worker が完全停止しているため、 配布物の attach 検証ができない。 次セッションは「iRMC SMB worker をどう復活させるか」 が core issue。
2. **🎯 iRMC FW 9.08F の SMB worker 完全停止条件**: 連続失敗で給与 give-up → Manager.Reset でも復活しない `永久 give-up state` がある。 本ハードウェアの再現条件は調査未了 (前セッション報告では「256s で復帰」とあったので、 今回は別要因の可能性も。 物理電源切離が安全策)
3. **`sudo` パスワード必須環境では deploy が detour する**: ユーザ提供 10.1.6.6 (passwordless sudo) は build / 検証に最適だが、 iRMC が 10.1.6.6 を SMB target として認識しない場合の deploy 先は 10.1.6.1 (sudo 必須) になる。 次セッション開始時に `sudo` 用パスワード or pre-deploy 済 patched smbd を確認
4. **iRMC ↔ 10.1.6.6 ネットワークは正常 (網ではなく FW 起因)**: ping / nc 22 / nc 443 すべて成功 + 同期 tcpdump で ICMP 観測。 つまり「10.1.6.6 で SMB を受ければ何か起きる」状態は作れている (iRMC が試みれば)
5. **build host 4 GB RAM + 4 cores で十分 (`make -j2`)**: Ubuntu 24.04 + apt build-dep samba + ./configure (1m37s) + make -j2 (11m27s) で OOM 起きず完走。 swap 3 GB のうち消費はピーク 1 GB 程度
6. **build artifact の RUNPATH は build dir 固定**: 10.1.6.1 へ持ち込む際は `chrpath -r /usr/lib/x86_64-linux-gnu/samba` or shared/private 全体を `LD_LIBRARY_PATH` 経由で見せる必要あり ([install-instructions.md](attachment/2026-05-21_055913_tx1320_raid10_smb_n6_step2_blocked/install-instructions.md))
7. **iRMC InternalEventLog で SMB worker 起動を確認できない (FW 9.08F の制約)**: SMB connection attempt や failure は log に残らないため、 検証は tcpdump + samba debug log + `ss -tn` の三点監視が必要
8. **`tcpdump &` (SSH background) は失敗する**: SSH session 終了で remote tcpdump も SIGHUP で死ぬ。 `nohup` + `< /dev/null` でも信頼できないことがある。 同期 (foreground) tcpdump が最も確実 (本セッションで実証)
