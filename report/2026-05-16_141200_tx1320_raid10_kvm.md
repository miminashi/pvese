## 前提・目的

親レポート (#68 後続) の「BIOS UEFI 化」は完了。 残課題の RAID10 構成 (BIOS UEFI HII の AVAGO MegaRAID Configuration Utility 経由) は **VGA frame buffer が更新されない問題** で挫折していた。

ユーザ確定方針 (本セッション開始時):

- アプローチ: **BMC Manager Reset → KVM 自動化リトライ** (Live OS + storcli は選択しない)
- 終着点: **RAID10 VD0 作成完了まで** (OS install は別セッション)
- Manager Reset 許可、 BMC ファクトリーリセットは禁止
- bios-setup / perc-raid skill の手法 (同セッション完結、 screenshot-each、 長め wait、 frame refresh) を参考にする

## 環境情報

- BIOS: V5.0.0.11 R1.22.0 (Aptio Setup Utility, UEFI 2.4 / PI 1.3、 UEFI 化済み)

## 実施内容と結果

### Phase 0: BMC Manager Reset 経路確定 (完了)

**新発見**: `/redfish/v1/Managers/iRMC` の Actions セクションには **`#Manager.Reset`** が `target` のみで AllowableValues 未掲載 (標準 Redfish なら ResetType@Redfish.AllowableValues がある)。 実機検証で **`{"ResetType":"GracefulRestart"}` が HTTP 204 で受理**、 BMC ソフトリブートが走った。 OEM `Actions/Oem/FTSManager.*` には `FWUpdate`, `AddLicense`, `VirtualMediaServiceRestart` 等はあるが `FTSManager.Reset` は無し。

```sh
curl -sS -k --ciphers DEFAULT@SECLEVEL=0 -u claude:Claude123 \
    -X POST -H 'Content-Type: application/json' \
    -d '{"ResetType":"GracefulRestart"}' \
    "https://10.254.254.9/redfish/v1/Managers/iRMC/Actions/Manager.Reset"
# → HTTP 204
```

**復帰時間: 187 秒** (10.254.254.9 への curl が HTTP 200 を返すまで)。 BMC ユーザ・ネットワーク設定は保持される (ファクトリーリセットではない)。

### Phase 1: `scripts/irmc-kvm-interact.py` 機能強化 (完了)

`bios-setup` skill の `bmc-kvm-interact.py` から学んだパターンを移植:

| 追加機能 | 用途 |
|---------|------|
| `release-kvm` / `reopen-kvm` step | `run_shell()` 内で viewer page を close/open。 `context`/`sid` を伝搬 (signature 拡張) |
| `--screenshot-each <prefix>` | sendkeys/combo/hold の後に PNG 保存 (連番 _001 から) |
| `force-refresh:<path>` step | Control x3 (50ms 間隔) + `canvas.dispatchEvent(new Event('resize'))` で frame full 誘発 |
| `capture_with_retry()` | PNG <8KB or canvas pixel sum <1000 を black 判定 → force-refresh → 3 回 retry |
| `assert-canvas:WxH[,sec]` step | 期待解像度に達するまで polling (force-refresh 自動挿入) |
| `oem-shot:` step に 3 段 retry | subprocess.run 単体失敗時に 2s sleep → 再試行 (最大 3 回) |

これら拡張は **ホスト Off 状態で smoke test 通過**:

```sh
.venv/bin/python scripts/irmc-kvm-interact.py \
    --bmc-ip 10.254.254.9 --bmc-user claude --bmc-pass Claude123 --timeout 30 \
    shell "wait:3; screenshot:tmp/<sid>/smoke.png; force-refresh:tmp/<sid>/forced.png; assert-canvas:200x200,5"
# → canvas 800x600 OK、 force-refresh + assert-canvas 動作確認
```

並行で `scripts/irmc-oem-screenshot.sh` を改修:

- **wall-clock 化**: 元は iteration count で elapsed を増やしていたため curl `--max-time` 遅延を被ると実時間が爆発 (最悪 14 分)。 `date +%s` で実時間 polling
- **multi-attempt retry**: 1 attempt の poll_timeout を 5-15s、 失敗時に Make を再 POST して再 polling、 最大 3-4 attempts

### 重要な発見

#### (A) BMC Manager Reset で VGA frame buffer 問題は **改善しない**

Plan の最大の賭けが外れた。 Manager Reset 後の BIOS Setup HII で canvas は引き続き黒 (`S3_settled.png` 18898 bytes はほぼ全面黒、 中央上に時計のみ表示)、 各 step で取った PNG はすべて 11857 bytes (canvas 800x600 の真っ黒画像)。

Aptio HII の GOP / EFI_GRAPHICS_OUTPUT_PROTOCOL が **BMC 側に frame を再送しない** 仕様と推定。 viewer release/reopen でも改善せず (WebSocket 再接続後の初期 frame も同じ黒)。

#### (B) OEM Screenshot は **約 3 回に 1 回成功** する (retry 必須)

これは Plan が最初に書いていた「最初の 1 回成功、 以降 AllowableValues Preview 遷移失敗」より良いニュース。 **retry を実装すれば成功率は実質 100% に近い**:

```
oem-shot d1  → OK (128304 bytes, Aptio Main 画面が見える)
oem-shot d2  → FAIL (Preview AllowableValues に遷移せず)
oem-shot d3  → FAIL
oem-shot d4  → OK (84174 bytes、 d3 までナビした位置)
oem-shot d5-d6 → FAIL
oem-shot d7  → OK (82333 bytes)
oem-shot d8-d9 → FAIL
oem-shot d10 → OK (81877 bytes、 Network Stack Configuration ハイライト)
oem-shot d11 → OK (127180 bytes、 Option ROM Configuration)
```

#### (C) BMC overload で全 Redfish/Web UI が無応答になる (60-90s)

連続して OEM Screenshot Make POST を投げると BMC capture pipeline が詰まり、 `curl https://<bmc>/redfish/v1/` が timeout (HTTP 000) するようになる。 60-90 秒待てば自動回復 (人手介入不要)。 対策: poll_timeout を短く (5s) して early fail、 BMC を休ませる。

#### (D) 新規 viewer session の最初の sendkeys が swallowed されることがある

1 viewer session 内で連続 sendkeys したものは確実に効く (explore-advanced.sh で 13 ArrowDown が確実に効いた)。 ただし、 別の Bash 呼出で新規 viewer を開いて 1 sendkeys + oem-shot をすると、 cursor が動いていないケース観測。 仮説: canvas focus 確立に時間がかかる。 対策: 冒頭に `wait:5; oem-shot:initial.jpg;` で canvas refresh + focus 確立してから sendkeys を送る。

#### (E) BIOS Setup Advanced の AVAGO MegaRAID 行は **ArrowDown 14 回**で到達 (空行 skip)

Aptio HII のメニュー (Advanced タブ):

| Down | エントリ |

### 2. AVAGO HII 内のキーシーケンス確定 (実機未確認)

推定 (LSI MegaRAID SAS3008 一般操作からの推定):

- Main Menu → `Configuration Management` (1番目?) → Enter
- Configuration Management → `Create Virtual Drive` (1番目?) → Enter
- Create Virtual Drive form:
  - RAID Level: Tab → Enter (popup) → ArrowDown まで `RAID 10` → Enter
  - Drives: Tab → Space (4本選択、 各 ArrowDown 間) → Apply Changes: Tab → Enter
  - Size: default OK → Tab → Save Configuration: Enter → Confirm Yes

これらの ArrowDown / Tab 回数は次セッションの実機検証で確定する必要あり。 `config/training_tx1320.yml` の `raid_setup.*_arrowdown` / `raid_setup.*_tab` に書き込めば `setup-raid10` の S6-S8 が自動進行する。

### 3. 代替経路 (推奨次手)

KVM 経路が更に時間を要する場合、 **OS Live ISO + `storcli` 路線への切替**:

- Debian Live (UEFI ブート) を `scripts/irmc-virtualmedia.sh` でマウント
- boot-override Cd UEFI + cycle で Live boot
- SOL 経由でログイン → broadcom 公式 `storcli` をインストール
- `storcli /c0 add vd r10 size=all drives=8:0,8:1,8:2,8:3 strip=64 wb ra direct` で RAID10 作成

pvese 内に複数の Live boot 実例あり (10-13号機 Phase 4 SED 検証等)。

### 4. RAID10 VD0 作成後の検証
